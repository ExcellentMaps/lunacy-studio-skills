## Автообновления безопасности

Большинство успешных взломов используют уязвимости, для которых давно вышло
исправление. Ставить его вручную никто не успевает — значит, это должно происходить
само.

```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades
```

Настройки — `/etc/apt/apt.conf.d/50unattended-upgrades`. Разумный вариант: ставить
**только** обновления безопасности, а не всё подряд.

```
Unattended-Upgrade::Allowed-Origins {
    "${distro_id}:${distro_codename}-security";
};
Unattended-Upgrade::Mail "почта@пример.ru";
Unattended-Upgrade::Automatic-Reboot "false";
```

| Строка | Что означает |
|---|---|
| `-security` | Только исправления безопасности. Обычные обновления функций не ставятся — меньше шанс, что что-то изменится в поведении |
| `Mail` | Письмо о том, что было поставлено. Без него обновления идут молча |
| `Automatic-Reboot "false"` | Сервер не перезагружается сам. Безопаснее для боевой машины: перезагрузку вы планируете |

Проверить, что механизм работает:

```bash
sudo unattended-upgrades --dry-run --debug | tail -20
grep -c ' Packages that will be upgraded' /var/log/unattended-upgrades/unattended-upgrades.log
```

### Когда обновлять руками

Автоматика не покрывает всё. Руками — в трёх случаях:

1. **Обновления ядра.** Ставятся автоматически, но начинают действовать только после
   перезагрузки. Проверить, нужна ли она: `ls /var/run/reboot-required` — если файл
   есть, перезагрузка назрела.
2. **Крупные обновления версии дистрибутива.** Меняют поведение служб, делаются
   осознанно и с проверкой после.
3. **Зависимости приложения** — `npm`, `pip`, `composer`. Их система не обновляет
   вообще, это отдельная работа: `guard-audit`, блок 4.

⚠️ Обновление всегда может что-то сломать. Перед `apt upgrade` на боевой машине —
снапшот в панели хостинга, если он доступен. Откат: восстановление снапшота, либо
`sudo apt install пакет=предыдущая.версия` для конкретного пакета.

## Ротация логов

Логи растут постоянно. Без ротации это оборачивается двумя проблемами, и обе —
про безопасность:

**Кончается место.** Диск, заполненный на 100%, останавливает всё: база не пишет,
nginx не пишет, certbot не продлевает сертификат, приложение падает. Выглядит как
загадочная авария, лечится одной командой `du`, а причиной оказывается лог в 40 ГБ.

**Накапливаются персональные данные.** Лог за три года — это база телефонов, адресов
и имён в открытом виде, лежащая рядом с сайтом. Её никто не защищает, потому что
никто про неё не думает.

Logrotate обычно уже установлен и уже настроен для nginx. Проверить:

```bash
cat /etc/logrotate.d/nginx
sudo logrotate -d /etc/logrotate.d/nginx     # -d = проверка, ничего не меняет
```

Свой файл для приложения — `/etc/logrotate.d/myapp`:

```
/var/log/myapp/*.log {
    daily                 # проверять раз в сутки
    rotate 14             # хранить 14 файлов, дальше удалять
    compress              # сжимать старые — место экономится в разы
    delaycompress         # предыдущий не сжимать: он ещё может быть открыт
    missingok             # нет файла — не считать ошибкой
    notifempty            # пустой не ротировать
    create 640 www-data adm
}
```

Срок `rotate 14` выбирается не наугад: слишком короткий — нечего смотреть при разборе
инцидента, слишком длинный — растёт объём персональных данных. Две недели для журнала
доступа и месяц для журнала ошибок — рабочая отправная точка.

Сколько занимают логи прямо сейчас:

```bash
sudo du -sh /var/log/* | sort -rh | head -10
df -h /
```

## ⚠️ Персональные данные в логах

Логи веб-сервера пишут полный адрес запроса. Если у вас поисковая строка или фильтр
передаются в адресе — в лог попадают телефоны, фамилии, номера договоров. Если в адресе
передаются токены — в лог попадают токены.

Хуже того: тот же лог читает система мониторинга, он уезжает в резервные копии и в
сторонние сервисы сбора логов, где живёт по своим правилам хранения.

Что с этим делать:

- передавать чувствительные значения в теле POST-запроса, а не в адресе — тогда в лог
  попадёт только путь;
- убедиться, что приложение не пишет в лог содержимое форм и заголовок `Authorization`
  целиком — это частая настройка по умолчанию в отладочном режиме, забытая на бою;
- ограничить срок хранения тем, что реально нужно для разбора инцидентов;
- в nginx при необходимости завести отдельный формат лога без строки запроса для
  конкретных путей.

Проверить, что уже накопилось:

```bash
sudo grep -ohE '[0-9]{10,11}' /var/log/nginx/access.log | head -5
sudo grep -ci 'authorization' /var/log/nginx/access.log
```

## Что мониторить

Пять вещей. Каждая ломается тихо, и каждая обнаруживается слишком поздно, если её
не смотреть.

| Что | Почему важно | Как проверить |
|---|---|---|
| Место на диске | Заполненный диск останавливает всё разом | `df -h /` — тревога при 85% |
| Срок сертификата | Истёк — браузер показывает клиентам предупреждение | `openssl … -enddate`, тревога при остатке < 20 дней |
| Доступность сайта | Упал ночью — узнать утром от клиента плохо | Внешний мониторинг, раз в минуту |
| Всплеск 401 / 403 / 429 | Кто-то целенаправленно долбится | Подсчёт по логу за сутки |
| Неудачные входы по SSH | Появилась целевая попытка, а не фоновый шум | `grep 'Failed password'` |

Простой ежедневный отчёт в cron:

```bash
#!/bin/bash
# /usr/local/bin/daily-check.sh — выполняется раз в сутки, ничего не меняет
DOM=ваш-домен.ru
echo "Диск:  $(df -h / | awk 'NR==2{print $5}')"
echo "Серт.: $(echo | openssl s_client -servername $DOM -connect $DOM:443 2>/dev/null \
        | openssl x509 -noout -enddate | cut -d= -f2)"
echo "429 за сутки: $(grep -c ' 429 ' /var/log/nginx/access.log)"
echo "403 за сутки: $(grep -c ' 403 ' /var/log/nginx/access.log)"
echo "SSH-неудачи:  $(grep -c 'Failed password' /var/log/auth.log)"
```

```bash
sudo chmod +x /usr/local/bin/daily-check.sh
# в crontab: 0 8 * * * /usr/local/bin/daily-check.sh | mail -s "Сервер: сводка" почта@пример.ru
```

Смотреть надо не на абсолютные числа, а на изменения. Сто 403 в сутки на сайте, где
вчера их было три, — повод посмотреть логи. Сто 403 каждый день подряд — это фоновый
шум сканеров, и он нормален.

## Мониторинг аптайма

Внешняя проверка «отвечает ли сайт» — самый дешёвый и самый полезный вид мониторинга.
Бесплатных сервисов достаточно; подойдёт любой, который умеет проверять раз в минуту
и писать в почту или мессенджер.

Что стоит проверять помимо главной страницы: адрес, который реально обращается к базе
(например, `/api/health`). Главная может отдаваться из кеша и выглядеть живой при
мёртвой базе.

### ⚠️ Как не заблокировать собственный мониторинг

Проверка аптайма приходит с одного адреса, часто, и представляется не браузером.
Под это описание подпадают все три защиты из этого набора сразу:

| Что сработает | Как выглядит проблема | Что сделать |
|---|---|---|
| `limit_req` | Периодические 429, случайные ложные тревоги | Исключение по адресу мониторинга |
| Фильтр ботов по User-Agent | Постоянный 403, «сайт лежит» круглосуточно | Внести User-Agent или адрес в исключения (`guard-ai-policy`) |
| fail2ban | Адрес мониторинга забанен, тревоги прекратились совсем | Адрес в `ignoreip` |

Третий случай самый неприятный: тревоги просто перестают приходить, и это выглядит
точно так же, как «всё хорошо».

Порядок настройки: сначала узнать адреса и User-Agent своего мониторинга, внести их в
исключения — и только потом включать защиты. Проверка после включения:

```bash
sudo grep 'АДРЕС_МОНИТОРИНГА' /var/log/nginx/access.log | tail -5
sudo fail2ban-client status sshd | grep -i banned
```

В первой команде должны быть коды `200`. Если там `403` или `429` — исключение не
сработало, и его надо чинить до того, как вы начнёте полагаться на мониторинг.
