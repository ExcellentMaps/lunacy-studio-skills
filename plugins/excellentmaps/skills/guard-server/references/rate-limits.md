## Зачем это нужно

Человек за компьютером делает несколько запросов в секунду в момент открытия раздела и
почти ничего между ними. Программа делает сотни запросов в секунду часами.

Ограничение частоты — это правило «с одного адреса принимается разумное количество
запросов в секунду». Живой работе оно не мешает никогда, а трём типовым сценариям
мешает сразу:

| Сценарий | Как выглядит без лимита | С лимитом |
|---|---|---|
| Подбор пароля на странице входа | тысячи попыток в час, никто не замечает | несколько попыток в минуту — подбор становится бессмысленным по времени |
| Выкачивание базы через ваш же API | скрипт забирает всё за ночь | забирает медленно и заметно в логах |
| Случайная петля в своём коде | сервер ложится от собственного фронтенда | упирается в 429, сервер живёт |

Лимит не заменяет ни авторизацию, ни блокировку после N неудачных попыток. Он
выигрывает время и делает автоматику видимой.

## nginx: limit_req_zone и limit_req

Настройка состоит из двух частей. Первая — **зона** — объявляется один раз на уровне
`http` (в `nginx.conf` или отдельном файле в `conf.d/`):

```nginx
limit_req_zone $binary_remote_addr zone=общая:10m rate=10r/s;
```

Разбор по словам:

| Часть | Что означает простыми словами |
|---|---|
| `$binary_remote_addr` | Считаем отдельно по каждому адресу посетителя. Двоичная форма адреса занимает меньше памяти, чем текстовая — поэтому именно она |
| `zone=общая:10m` | Имя счётчика и сколько памяти ему выделено. Счётчик общий для всех рабочих процессов nginx |
| `10m` | 10 мегабайт — примерно 160 тысяч адресов одновременно. Для обычного сайта запас огромный |
| `rate=10r/s` | Десять запросов в секунду с одного адреса |

⚠️ Тонкость про `rate`: nginx понимает его не как «10 в течение секунды», а как «один
запрос раз в 100 миллисекунд». Одиннадцатый запрос, пришедший в ту же миллисекунду,
будет отклонён, даже если за всю секунду их было всего одиннадцать. Именно для этого
нужна вторая часть настройки.

Вторая часть — **применение** — внутри `server` или `location`:

```nginx
location /api/ {
    limit_req zone=общая burst=20 nodelay;
    limit_req_status 429;
    proxy_pass http://127.0.0.1:8000;
}
```

| Часть | Что означает |
|---|---|
| `burst=20` | Очередь на 20 запросов сверх лимита. Открытие раздела шлёт десяток запросов сразу — это нормально и должно проходить |
| `nodelay` | Запросы из очереди обрабатываются немедленно, а не растягиваются по одному в 100 мс. Без него интерфейс начнёт заметно подтормаживать |
| `limit_req_status 429` | Какой код вернуть при превышении. По умолчанию nginx отдаёт 503 |

**Почему именно 429.** Код 429 означает «слишком много запросов, попробуйте позже» —
это ровно то, что произошло. Код 503 означает «сервис недоступен», и его увидят иначе:
мониторинг посчитает сайт упавшим, поисковики — временно неработающим, а разработчик
полдня будет искать несуществующую аварию.

## Отдельная строгая зона на страницу входа

Вход — это место, где живой человек делает от силы несколько попыток, а программа
подбора делает тысячи. Поэтому лимит там должен быть в разы строже общего:

```nginx
# Рядом с общей зоной, на уровне http
limit_req_zone $binary_remote_addr zone=вход:10m rate=10r/m;
```

`10r/m` — это десять запросов в **минуту**, то есть один раз в шесть секунд. Человек,
который ошибся паролем два раза подряд, в такой лимит не упирается.

```nginx
location = /api/auth/login {
    limit_req zone=вход burst=5 nodelay;
    limit_req_status 429;
    proxy_pass http://127.0.0.1:8000;
}
```

Зоны не мешают друг другу: можно применить в одном месте обе, тогда запрос должен
пройти обе проверки.

⚠️ Указывайте точный путь (`location = /api/auth/login`), а не каталог. Строгий лимит,
случайно накрывший весь `/api/`, сделает интерфейс неработоспособным.

## limit_conn: одновременные соединения

`limit_req` считает запросы, `limit_conn` — открытые соединения. Нужен там, где один
запрос живёт долго: скачивание файлов, экспорт, длинные отчёты.

```nginx
limit_conn_zone $binary_remote_addr zone=соединения:10m;   # на уровне http

location /files/ {
    limit_conn соединения 10;      # не больше 10 одновременных закачек с адреса
    limit_conn_status 429;
}
```

Без него один клиент может занять все свободные соединения сервера десятком
параллельных закачек, и остальным просто не хватит места.

## Как подобрать цифры

⚠️ **Сначала посмотреть реальную нагрузку, потом ставить лимит.** Взятые с потолка
цифры либо не мешают никому, включая перебор, либо ломают работу людям — и второе
обнаруживается в худший момент.

Сколько запросов в секунду даёт самый активный адрес за сегодня:

```bash
sudo awk '{print $1, $4}' /var/log/nginx/access.log \
  | cut -d: -f1-3 | sort | uniq -c | sort -rn | head -20
```

Первая колонка — число запросов за минуту с одного адреса. Делите на 60 — получаете
запросы в секунду. Разумный лимит — примерно вчетверо выше наблюдаемого пика живых
пользователей.

Порядок внедрения:

1. Поставить лимит заведомо мягкий — вчетверо выше пика.
2. Через сутки посмотреть, сколько 429 выдано: если ноль, можно ужесточать;
   если есть — проверить, кому именно они достались.
   ```bash
   sudo grep ' 429 ' /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
   ```
3. Ужесточать по одному шагу, каждый раз проверяя логи. Не наоборот.

**Откат:** закомментировать строку `limit_req` в нужном `location`,
`nginx -t && systemctl reload nginx`. Действует немедленно, ничего не запоминается
ни у пользователей, ни на сервере.

Отдельно стоит завести исключение по адресу для мониторинга и офиса — иначе
собственная проверка аптайма упрётся в лимит и начнёт слать ложные тревоги.

## Вариант для Caddy

В штатной поставке Caddy ограничения частоты нет — нужен сторонний модуль
`caddy-ratelimit`, который встраивается при сборке через `xcaddy`. Это не «плагин из
магазина», а пересборка исполняемого файла, и это стоит учитывать при выборе.

```
ваш-домен.ru {
    rate_limit {
        zone общая {
            key    {remote_host}
            events 100
            window 10s
        }
    }
    reverse_proxy 127.0.0.1:8000
}
```

`events 100` и `window 10s` вместе читаются как «сто запросов за десять секунд с
адреса» — то есть в среднем десять в секунду, с естественным допуском на всплески.
Отдельного `burst` здесь нет: окно само по себе его заменяет.

Если ставить модуль не хочется, разумная альтернатива — оставить Caddy для TLS и
статики, а ограничение частоты держать в приложении.

## Где лимит живёт на самом деле

Ограничение на nginx — **второй рубеж**. Оно считает запросы по адресу и ничего не
знает про то, что внутри: для него неудачный вход и удачный неотличимы.

Первый рубеж живёт в приложении и в базе, и он устроен иначе — по учётной записи, а не
по адресу:

- блокировка учётной записи после N неудачных попыток входа подряд;
- задержка, растущая с каждой следующей неудачной попыткой;
- ограничение числа выгрузок и экспортов на пользователя в сутки;
- ограничение выдачи на один запрос к API, чтобы базу нельзя было забрать одним
  обращением.

Причина проста: адрес меняется. Перебор с тысячи адресов по одной попытке с каждого
не упрётся ни в один лимит по адресу, но упрётся в счётчик неудачных попыток по
конкретной учётной записи. Настройка лимитов на nginx не отменяет этой работы — она
покупает на неё время.
