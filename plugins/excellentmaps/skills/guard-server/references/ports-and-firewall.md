## ⚠️ Прочитать до первой команды

Работа с firewall — единственное место в этом наборе, где неверный порядок действий
отрезает вас от сервера **мгновенно и полностью**. Не «замедляет», не «ломает сайт», а
именно отрезает: SSH-сессия умирает, новая не устанавливается, и сделать с машиной
ничего нельзя.

Три правила, которые снимают почти весь риск:

1. **Откройте вторую сессию на сервер и не закрывайте её.** Первая — рабочая, в ней вы
   вносите изменения. Вторая — спасательная, она уже установлена и переживёт правило,
   которое запретит новые подключения. Через неё вы откатите то, что сломали.
2. **Сначала разрешить SSH, потом включать firewall.** Именно в таком порядке:
   ```bash
   sudo ufw allow OpenSSH        # или: sudo ufw allow 22/tcp
   sudo ufw status               # убедиться, что правило в списке
   sudo ufw enable               # только теперь
   ```
   `ufw enable` без разрешённого SSH включает политику «входящее запрещено всё» — и
   ваше собственное подключение попадает под неё первым.
3. **Если панель хостинга умеет снапшоты — сделайте снапшот перед началом.**

**Если доступ всё-таки потерян.** Паниковать не нужно, сервер жив, недоступен только
SSH. Порядок: открыть панель хостинга → найти раздел «Консоль», «VNC» или «Web-терминал»
→ войти под root с паролем, который заводился при создании машины → выполнить
`ufw disable` → восстановить доступ → начать заново, уже со второй сессией. Если
консоли в панели нет — остаются только обращение в поддержку хостинга и переустановка,
поэтому проверьте наличие консоли **до** работы, а не после.

## Принцип: наружу смотрит одна дверь

Наружу — веб-сервер: порты 80 и 443. Плюс SSH, потому что вам нужно управлять машиной.
Всё остальное слушает `127.0.0.1` и доступно только самому серверу. Это не «защищено
паролем», а именно недоступно. Сервис, до которого нельзя дотянуться
из интернета, нельзя и взломать из интернета, каким бы дырявым он ни был. Сервис,
открытый наружу, находят автоматические сканеры в первые часы после запуска — не потому
что кто-то нацелился именно на вас, а потому что весь диапазон адресов сканируется
непрерывно.

## Что не должно отвечать снаружи никогда

| Порт | Что это | Что бывает, когда открыт |
|---|---|---|
| 5432 | PostgreSQL | Подбор пароля круглосуточно, при слабом — вся база |
| 3306 | MySQL / MariaDB | То же самое |
| 27017 | MongoDB | Исторически часто вообще без пароля |
| 6379 | Redis | По умолчанию без пароля; через него же исполняют команды |
| 9200 | Elasticsearch | Обычно без авторизации: вся индексация читается и стирается |
| 2375 | Docker API без TLS | 🔴 Полный контроль над сервером без единого пароля |
| 5672 / 15672 | RabbitMQ и его панель | Очередь и учётки по умолчанию |
| 9090 / 3000 | Prometheus, Grafana | Метрики выдают внутреннее устройство системы |
| 8080 / 8000 | Сервер приложения напрямую | Обход всех правил, заголовков и лимитов nginx |
| 9000 | Portainer, FPM-статус | Панель управления контейнерами |

Плюс всё, что называется «панель», «админка», «dashboard», «status», «metrics»,
«debug» — независимо от порта.

## Как перевести службу на 127.0.0.1

### PostgreSQL

В `postgresql.conf` (обычно `/etc/postgresql/16/main/postgresql.conf`):

```
listen_addresses = 'localhost'
```

```bash
sudo systemctl restart postgresql
ss -tulpn | grep 5432        # ожидаем 127.0.0.1:5432
```

Откат: вернуть прежнее значение и перезапустить. Перед правкой — `sudo cp
postgresql.conf postgresql.conf.bak`.

### Redis

В `/etc/redis/redis.conf`:

```
bind 127.0.0.1 ::1
protected-mode yes
```

```bash
sudo systemctl restart redis-server
```

### Docker и docker-compose

Было — открыто в интернет:

```yaml
ports:
  - "5432:5432"
```

Стало — доступно только серверу:

```yaml
ports:
  - "127.0.0.1:5432:5432"
```

А если к службе обращается только другой контейнер из той же сети, `ports:` не нужен
вовсе — достаточно `expose:`, и порт не появится на хосте.

```bash
docker compose up -d
docker ps --format '{{.Names}}\t{{.Ports}}'
```

⚠️ Повтор важного из `recon.md`: Docker пишет правила в iptables мимо ufw, поэтому
`ufw status` **не является** доказательством закрытого порта. Доказательство — проверка
с другой машины.

## ufw по шагам

Ufw — это удобная надстройка над iptables. Он не даёт ничего, чего нельзя сделать
руками, но резко снижает шанс ошибиться.

```bash
# 1. Посмотреть, что есть сейчас
sudo ufw status verbose

# 2. Политика по умолчанию: входящее запрещено, исходящее разрешено
sudo ufw default deny incoming
sudo ufw default allow outgoing

# 3. ⚠️ СНАЧАЛА SSH
sudo ufw allow OpenSSH

# 4. Сайт
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# 5. Проверить список ДО включения
sudo ufw show added

# 6. Включить
sudo ufw enable
```

После включения — не закрывая вторую сессию — открыть третью и убедиться, что она
устанавливается. Только после этого можно считать шаг завершённым.

Доступ к служебному порту только с одного адреса (например, к базе с офисного IP):

```bash
sudo ufw allow from 203.0.113.7 to any port 5432 proto tcp
```

Это допустимо, но слабее, чем `127.0.0.1` плюс SSH-туннель: домашние и офисные адреса
у провайдеров меняются, а правило остаётся.

**Откат для ufw.** Любое правило снимается по номеру:

```bash
sudo ufw status numbered
sudo ufw delete 3
```

Полностью выключить: `sudo ufw disable`. Сбросить все правила и начать с нуля:
`sudo ufw reset` — ⚠️ она же удалит и разрешение SSH, поэтому выполняется только при
открытой второй сессии и сразу с последующим `ufw allow OpenSSH`.

## Облачный firewall — второй рубеж

Почти у всех хостингов есть свой firewall на уровне сети: «группы безопасности»,
«сетевые правила», «облачный firewall». Он работает **до** того, как трафик доходит до
машины, и у него два важных отличия от ufw:

- его не обходит Docker — правила применяются вне сервера;
- его нельзя сломать изнутри сервера, и правится он из панели, а не по SSH, то есть
  заблокировать себя им проще, но и разблокироваться быстрее.

Разумная схема — оба рубежа: в панели хостинга разрешены 22, 80, 443, и ровно то же
самое продублировано в ufw. Совпадающие правила не мешают друг другу.

⚠️ При настройке облачного firewall действует то же правило: сначала добавить правило
для 22 порта, потом менять политику по умолчанию.

## Проверка результата

С **другой машины**:

```bash
nc -zv ваш-домен.ru 443        # должен ответить
nc -zv ваш-домен.ru 5432       # должен молчать
nc -zv ваш-домен.ru 6379       # должен молчать
```

Если база закрыта, а вам нужно к ней подключиться со своего ноутбука — это делается
SSH-туннелем, без единого открытого порта:

```bash
ssh -L 5432:127.0.0.1:5432 пользователь@ваш-домен.ru
# дальше локальный клиент подключается к 127.0.0.1:5432
```

Туннель живёт, пока открыта SSH-сессия, и закрывается вместе с ней — снаружи в это
время по-прежнему ничего не видно.
