## ⚠️ Прочитать до первой команды

Всё на этой странице меняет способ входа на сервер. Ошибка здесь не ломает сайт — она
закрывает **вам** дорогу к машине.

1. **Откройте вторую сессию и не закрывайте её до конца работы.** Уже установленное
   SSH-соединение переживает и перезапуск службы, и запрет парольного входа. Через него
   вы откатите неудачную правку. Новую сессию после изменения конфига открывайте
   **третьим** окном, не трогая вторую.
2. **Проверьте, есть ли у вашего хостинга консоль в панели** («Console», «VNC»,
   «Web-терминал»). Это единственный путь назад, если умрут обе сессии. Если консоли
   нет, работайте особенно аккуратно и обязательно сделайте снапшот.
3. **Перед правкой конфига — копия:**
   ```bash
   sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak
   ```
   Откат из второй сессии:
   ```bash
   sudo cp /etc/ssh/sshd_config.bak /etc/ssh/sshd_config
   sudo systemctl restart ssh
   ```

## Вход по ключу вместо пароля

Пароль можно подобрать: он короткий, и пробовать можно бесконечно. Ключ подобрать
нельзя — он слишком длинный, чтобы перебор имел смысл. Это единственное изменение на
странице, которое действительно меняет картину; всё остальное — дополнения.

### 1. Сгенерировать ключ на своей машине

```bash
ssh-keygen -t ed25519 -C "имя@ваш-компьютер"
```

Тип `ed25519` — современный, короткий и быстрый. Старый `rsa` тоже работает, но
выбирать его для нового ключа незачем. На вопрос про passphrase лучше ответить
парольной фразой: она шифрует сам файл ключа, и украденный ноутбук не даёт вору
доступа к серверу. Вводить её каждый раз не придётся — этим занимается `ssh-agent`.

Получается пара файлов: `~/.ssh/id_ed25519` — закрытая часть, её никому и никогда, и
`~/.ssh/id_ed25519.pub` — открытая, её кладут на сервер.

### 2. Положить открытую часть на сервер

```bash
ssh-copy-id пользователь@ваш-домен.ru
```

Если `ssh-copy-id` недоступен, то же самое руками:

```bash
cat ~/.ssh/id_ed25519.pub | ssh пользователь@ваш-домен.ru \
  "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

Права важны: при слишком свободных правах на `~/.ssh` или `authorized_keys` sshd молча
откажется использовать ключ, и вы будете искать причину в конфиге.

### 3. ⚠️ Проверить, что ключ работает, ДО отключения пароля

Самый важный шаг страницы. В **новом** окне:

```bash
ssh -o PasswordAuthentication=no пользователь@ваш-домен.ru
```

Флаг запрещает клиенту переходить на пароль. Вход прошёл — ключ действительно работает.
Появилось `Permission denied (publickey)` — ключ не работает, и отключать парольный
вход сейчас нельзя ни в коем случае.

## Отключить вход по паролю

Только после успешной проверки из шага 3. В `/etc/ssh/sshd_config`:

```
PasswordAuthentication no
PubkeyAuthentication yes
PermitRootLogin prohibit-password
```

| Строка | Что делает |
|---|---|
| `PasswordAuthentication no` | Вход по паролю запрещён полностью. Перебор паролей перестаёт иметь смысл |
| `PubkeyAuthentication yes` | Вход по ключу разрешён (обычно уже так, но пусть будет явно) |
| `PermitRootLogin prohibit-password` | Root может войти только по ключу. Значение `no` — строже, но тогда root-доступ должен быть у обычного пользователя через `sudo` |

Проверить синтаксис и применить:

```bash
sudo sshd -t                  # синтаксис; молчание = всё в порядке
sudo systemctl reload ssh     # reload мягче restart: живые сессии не рвутся
sudo sshd -T | grep -iE 'passwordauthentication|permitrootlogin'
```

⚠️ На многих системах настройки лежат не только в `sshd_config`, но и в файлах
`/etc/ssh/sshd_config.d/*.conf`, которые подключаются **выше** по файлу и потому
выигрывают. Поэтому проверять результат надо командой `sshd -T`, показывающей
действующую конфигурацию, а не чтением файла глазами.

## Про нестандартный порт — честно

Перенос SSH с 22 порта на, скажем, 2222 делает ровно одну вещь: убирает из логов
сплошной поток попыток от массовых сканеров, которые ходят только по 22. Логи
становятся читаемыми, и настоящая целенаправленная попытка в них наконец видна.
Защитой это не является: целевое сканирование находит открытый порт за секунды,
независимо от номера. Меняйте порт ради тишины в логах, а не вместо ключей и fail2ban.

⚠️ При смене порта: сначала `sudo ufw allow 2222/tcp`, потом менять `Port` в конфиге,
потом проверять вход в новом окне — и только потом убирать разрешение для 22.

## fail2ban: автоматическая блокировка

fail2ban читает логи и временно блокирует адреса, с которых идут неудачные попытки.
Ставится как `sudo apt install fail2ban`. Свои настройки пишут в
`/etc/fail2ban/jail.local` — файл `jail.conf` перезаписывается при обновлении пакета,
`jail.local` нет.

```ini
[DEFAULT]
bantime  = 1h
findtime = 10m
maxretry = 5
ignoreip = 127.0.0.1/8 203.0.113.7      # ← свой офисный адрес, чтобы не забанить себя

[sshd]
enabled = true

[nginx-http-auth]
enabled = true

[nginx-limit-req]
enabled  = true
logpath  = /var/log/nginx/error.log
maxretry = 10
```

| Параметр | Что означает |
|---|---|
| `maxretry = 5` | Пять неудачных попыток... |
| `findtime = 10m` | ...в течение десяти минут... |
| `bantime = 1h` | ...и адрес блокируется на час |
| `ignoreip` | Адреса, которые не блокируются никогда |

Секция `[nginx-limit-req]` подхватывает записи, которые оставляет `limit_req` из
`rate-limits.md`: тот, кто регулярно упирается в лимит, блокируется целиком.

```bash
sudo systemctl enable --now fail2ban
sudo fail2ban-client status         # какие jail включены
sudo fail2ban-client status sshd    # кто заблокирован прямо сейчас
```

### ⚠️ Если заблокировали сами себя

Происходит регулярно: несколько раз ошиблись паролем или тестировали лимиты.
Сервер при этом жив, просто ваш адрес в списке. Способы, по порядку доступности:

1. **С другого адреса** — мобильный интернет, VPN, другой сервер:
   ```bash
   sudo fail2ban-client set sshd unbanip ВАШ_АДРЕС
   ```
2. **Через консоль в панели хостинга** — та же команда;
3. Если консоли нет и другого адреса нет — подождать `bantime`. Именно поэтому
   `bantime = 1h`, а не сутки: час пережить можно.

Профилактика: внести свои постоянные адреса в `ignoreip` **до** запуска fail2ban.

## Отдельные учётные записи вместо общего root

Когда все ходят под root с одним паролем, в логах нет ответа на вопрос «кто это сделал».
Уволенному сотруднику нельзя отозвать доступ, не меняя его всем сразу.

```bash
sudo adduser ivan && sudo usermod -aG sudo ivan
sudo mkdir -p /home/ivan/.ssh && sudo chmod 700 /home/ivan/.ssh
# положить его открытый ключ в /home/ivan/.ssh/authorized_keys, затем:
sudo chown -R ivan:ivan /home/ivan/.ssh
sudo chmod 600 /home/ivan/.ssh/authorized_keys
```

Дальше каждый входит под собой, повышает права через `sudo`, и в `/var/log/auth.log`
видно, кто и что делал. Ключи у каждого свои — общих не бывает.

### Отзыв доступа

```bash
sudo usermod -L ivan                      # заблокировать пароль
sudo rm /home/ivan/.ssh/authorized_keys   # убрать ключ — главное
sudo pkill -u ivan                        # закрыть его текущие сессии
```

Удаление ключа обязательно: заблокированный пароль не мешает войти по ключу.

⚠️ Отзыв доступа к серверу — только половина работы. Вторая половина — ротация всех
общих секретов, которые человек знал: пароли баз, ключи API, доступы к панелям. Порядок
ротации — `secrets.md`.

## Итоговая проверка

```bash
sudo sshd -T | grep -iE 'passwordauthentication|permitrootlogin|pubkeyauthentication'
sudo fail2ban-client status sshd
sudo grep -c 'Failed password' /var/log/auth.log
```

Третья команда через неделю после настройки должна показывать заметно меньшее число.
