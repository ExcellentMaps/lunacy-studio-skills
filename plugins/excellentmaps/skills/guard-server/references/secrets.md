# Секреты, ключи и пароли

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

---

Секрет — это любая строка, знание которой даёт доступ: пароль базы, ключ API, токен
платёжного сервиса, приватный ключ, строка подключения целиком. Утечка одного такого
значения обнуляет всё остальное: можно идеально закрыть порты, настроить HTTPS и
firewall, и всё это не будет иметь значения, если сервисный ключ базы лежит в
публичном репозитории.

---

## Три правила

**1. Не в git. Никогда, ни в каком виде, даже временно.**
Git помнит всё. Удалить файл следующим коммитом недостаточно — он остаётся в истории и
достаётся оттуда одной командой. Если репозиторий хоть раз был публичным или его
клонировал хоть один человек, история уже не только у вас.

**2. Права `600`, владелец — тот, от кого работает сервис.**
`600` означает «читает и пишет только владелец». `644` — читает любой пользователь
системы, включая учётную запись веб-сервера и любой скрипт, запущенный от чужого имени.

```bash
sudo chown root:root /etc/myapp/secrets.env
sudo chmod 600 /etc/myapp/secrets.env
stat -c '%a %U:%G %n' /etc/myapp/secrets.env
```

**3. Утёк — значит скомпрометирован.**
Не «наверное, никто не заметил». Ключ, полежавший в публичном репозитории пять минут,
уже собран: боты сканируют новые коммиты на GitHub непрерывно, и промежуток между
публикацией и первым использованием чужого ключа измеряется минутами. Единственная
правильная реакция — ротация.

## Где хранить

| Способ | Когда подходит | На что смотреть |
|---|---|---|
| Файл вне веб-корня | Обычный сервер, один-два проекта | Права `600`, каталог не внутри `root` из конфига nginx |
| Переменные окружения systemd | Сервис запускается через systemd | Значения не видны в `ps`, в отличие от аргументов командной строки |
| Секреты Docker / compose | Контейнеры | Не путать с `environment:` — тот виден в `docker inspect` |
| Менеджер секретов (Vault, облачный) | Несколько серверов, команда, аудит | Заметно сложнее в настройке; для одного сервера избыточен |

### Файл вне веб-корня

Ключевое слово — «вне». Если `root` в конфиге nginx указывает на `/var/www/site`, то
файл секретов не должен лежать там ни под каким именем.

```bash
sudo mkdir -p /etc/myapp
sudo install -m 600 -o root -g root /dev/null /etc/myapp/secrets.env
sudo nano /etc/myapp/secrets.env
```

### Переменные окружения systemd

В юните сервиса:

```ini
[Service]
EnvironmentFile=/etc/myapp/secrets.env
```

Файл читается от root при запуске, само приложение работает от обычного пользователя и
доступа к файлу не имеет — только к уже загруженным значениям.

⚠️ Не передавайте секреты аргументами командной строки (`--password=…`): аргументы
видны в выводе `ps` любому пользователю системы.

## ⚠️ .env в корне сайта

Самая частая и самая дорогая ошибка из всех на этой странице.

Если файл `.env` лежит в каталоге, который веб-сервер отдаёт как сайт, он доступен по
прямой ссылке. Веб-сервер не знает, что этот файл особенный — для него это обычный
текст, и он честно отдаёт его любому, кто попросил. А просят постоянно: запрос
`/.env` — один из первых в списке любого автоматического сканера.

Проверить прямо сейчас, с любой машины:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://ваш-домен.ru/.env
```

`200` — 🔴 все ключи уже могли утечь, переходите к разделу про ротацию.

Правильное решение — **вынести файл за пределы веб-корня**. Запрет в конфиге — это
вторая линия на случай, если кто-то положит туда ещё один файл:

```nginx
# Скрытые файлы и каталоги: .env, .git, .htaccess, .DS_Store
location ~ /\. {
    deny all;
    access_log off;
    log_not_found off;
}
```

⚠️ Это правило заодно закрывает `/.well-known/acme-challenge/`, по которому продлевается
сертификат. Блок для него должен стоять **выше** в конфиге — в
`templates/nginx-security.conf` это учтено.

Отдельно проверьте `/.git/`: открытый каталог `.git` позволяет выкачать весь исходный
код вместе с историей, а значит и все секреты, которые когда-либо в ней были.

## Ротация: порядок имеет значение

Ротация — замена секрета на новый. Единственный правильный порядок:

**1. Выпустить новый.** Старый в этот момент ещё работает — ничего не падает.

**2. Обновить везде, где используется.** Все места сразу: сервер, файл окружения,
CI/CD, переменные в панели хостинга, фоновые задачи, скрипты бэкапа, машины
разработчиков. Пропущенное место обнаружится на шаге 3 — этим шаг 3 и полезен.

**3. Отозвать старый.** Только теперь.

⚠️ **Если отозвать старый первым, сервис упадёт немедленно** — и упадёт целиком, пока
вы в спешке ищете все места, куда этот ключ был вписан. Это самая частая причина
незапланированного простоя при работе с секретами, и она полностью устраняется
порядком действий.

Перед началом полезно составить список мест. Найти их помогает поиск по имени
переменной:

```bash
grep -rn 'DB_PASSWORD\|API_KEY' . --exclude-dir=node_modules --exclude-dir=.git
```

## Секрет уже в git. Что делать

Порядок здесь такой же жёсткий, как в предыдущем разделе, и по той же причине.

### Шаг 1. Ротация — первым делом

Не чистка истории. Именно ротация.

Причина простая: история репозитория уже склонирована. Она есть в чужих локальных
копиях, в кеше форков, в зеркалах CI, в индексах сканеров. Переписывание истории у вас
не меняет ни одну из этих копий. Пока секрет не отозван, он рабочий — независимо от
того, что показывает ваш репозиторий.

Поэтому: выпустить новый → обновить везде → отозвать старый. Ровно как выше.

### Шаг 2. Убрать файл из отслеживаемых

```bash
git rm --cached .env
echo '.env' >> .gitignore
git commit -m "секреты вынесены из репозитория"
```

Это останавливает утечку дальше, но не убирает старое значение из истории.

### Шаг 3. Почистить историю

Два рабочих инструмента:

```bash
# git-filter-repo — рекомендуемый способ
pip install git-filter-repo
git filter-repo --path .env --invert-paths

# BFG Repo-Cleaner — проще для одной задачи
bfg --delete-files .env
```

⚠️ Обе команды **переписывают историю**: у всех коммитов меняются идентификаторы. Что
из этого следует:

- всем участникам придётся заново клонировать репозиторий; попытка сделать `pull`
  в старую копию даст конфликт, разбирать который дольше, чем клонировать;
- открытые pull-request'ы, скорее всего, придётся пересоздать;
- перед началом нужна полная копия репозитория: `git clone --mirror` в сторону.

**Откат:** только из той самой копии `--mirror`. После `push --force` в общий
репозиторий откатиться больше нечем — поэтому копия делается до, а не после.

### Шаг 4. Проверить, что не осталось

```bash
git log --all --full-history -- .env
git grep -I 'BEGIN PRIVATE KEY' $(git rev-list --all) 2>/dev/null | head
```

## Генерация стойких значений

Придуманные человеком пароли предсказуемы. Генерируйте:

```bash
openssl rand -base64 32       # пароль/токен, ~43 символа
openssl rand -hex 32          # 64 шестнадцатеричных символа
openssl rand -base64 48       # длиннее, для подписи сессий и JWT
```

`-base64` удобнее читать и копировать, `-hex` безопаснее вставлять в конфиги, где
символы `+` и `/` могут потребовать экранирования.

Короткий ориентир по длине: пароль базы — от 24 символов, ключ подписи сессий — от 32
байт. Разные сервисы — разные значения: один общий пароль на всё превращает одну утечку
в полную компрометацию.
