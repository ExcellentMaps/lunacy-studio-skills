## Зачем это нужно

Без HTTPS всё, что уходит со страницы и приходит на неё, передаётся открытым текстом.
Прочитать его может любой, через чью сеть проходит трафик: владелец Wi-Fi в кафе,
провайдер, администратор офисной сети. Речь не только о паролях — видны имена
клиентов, телефоны, суммы, содержимое форм.

Второе, что даёт HTTPS, важнее первого: трафик нельзя **подменить**. Без шифрования
между человеком и сервером можно встать посередине, отдать браузеру свою версию
страницы и собрать логины на форме, которая выглядит точно как ваша.

Сертификат — подтверждение, что домен действительно ваш. Выдаётся бесплатно,
продлевается автоматикой, ручной работы после настройки не требует.

## Let's Encrypt через certbot

### Вариант 1: webroot — сайт уже работает

Подходит, когда nginx запущен и отдаёт сайт: останавливать ничего не нужно. В конфиг
nginx для 80 порта добавить путь, по которому проверяется владение доменом:

```nginx
location /.well-known/acme-challenge/ { root /var/www/certbot; }
```

```bash
sudo mkdir -p /var/www/certbot
sudo nginx -t && sudo systemctl reload nginx
sudo certbot certonly --webroot -w /var/www/certbot \
  -d ваш-домен.ru -d www.ваш-домен.ru \
  --email почта@пример.ru --agree-tos --no-eff-email
```

⚠️ Этот путь должен быть исключён из всех блокировок — фильтра ботов, rate-limit,
правил «запретить скрытые файлы». Иначе выпуск пройдёт, а через 90 дней продление
молча не сработает, потому что проверка упрётся в ваш же 403.

### Вариант 2: standalone — сайта ещё нет

Certbot сам поднимает временный веб-сервер на 80 порту, поэтому занимающую его
программу нужно на минуту остановить:

```bash
sudo systemctl stop nginx
sudo certbot certonly --standalone -d ваш-домен.ru \
  --email почта@пример.ru --agree-tos --no-eff-email
sudo systemctl start nginx
```

⚠️ Сайт недоступен, пока nginx остановлен. Для боевой машины выбирайте webroot.

### Куда кладутся файлы

`/etc/letsencrypt/live/ваш-домен.ru/fullchain.pem` — сертификат с цепочкой,
`privkey.pem` — закрытый ключ с правами `600`. В конфиге указываются именно пути
`live/…`: это ссылки, которые certbot переключает при продлении. Копировать файлы
куда-то ещё не нужно — копия не обновится.

## Автопродление и как убедиться, что оно работает

Certbot из пакета ставит таймер сам. Проверить, что таймер есть и запускается:

```bash
systemctl list-timers | grep certbot
```

Проверить само продление — вхолостую, ничего не меняя:

```bash
sudo certbot renew --dry-run
```

Эта команда проходит весь путь продления, но не устанавливает результат. Если она
завершилась успешно — через 90 дней всё пройдёт так же. Если упала, чинить надо
сейчас, а не когда сертификат истечёт.

После продления nginx должен перечитать файлы — иначе он продолжит отдавать старый
сертификат из памяти. Один раз, для всех будущих продлений, создаётся файл
`/etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh` из двух строк
(`#!/bin/sh` и `systemctl reload nginx`) с правами `chmod +x`.

⚠️ У Let's Encrypt есть ограничение на число выпусков одного набора доменов в неделю.
Поэтому отлаживать настройку надо на `--dry-run`, а не повторными боевыми выпусками.

## Редирект http → https

Отдельный блок на 80 порту, который ничего не отдаёт, кроме перенаправления и пути
проверки сертификата:

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name ваш-домен.ru;

    # Проверка владения доменом — должна остаться доступной
    location /.well-known/acme-challenge/ { root /var/www/certbot; }

    # Всё остальное — на https, с сохранением адреса страницы
    location / { return 301 https://$host$request_uri; }
}
```

Так на 80 порту не остаётся рабочей копии сайта. Если оставить — форма логина будет
доступна и по http, и часть людей (и все старые закладки) пойдут именно туда.

## Версии протокола

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers off;
ssl_session_cache shared:SSL:10m;
ssl_session_timeout 1d;
```

TLSv1.0 и 1.1 давно отключены в браузерах — включать их «для совместимости» смысла
нет: клиентов, которым это нужно, не осталось.

## HSTS — и почему не сразу большой срок

`Strict-Transport-Security` говорит браузеру: на этот сайт — только по защищённому
соединению, и запомни это на указанное время. После этого браузер не пойдёт по http
даже по прямой ссылке.

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
```

⚠️ **Запрет живёт в браузере пользователя, а не у вас на сервере.** Убрав заголовок,
вы не отмените его действие: браузер, который уже запомнил `max-age=31536000`, будет
отказываться открывать сайт по http ещё год. Если сертификат в этот момент просрочен
или сломан, люди увидят не сайт, а ошибку, и обойти её не смогут.

Поэтому порядок такой:

| Этап | Значение | Когда переходить дальше |
|---|---|---|
| 1 | `max-age=300` | Сразу после включения HTTPS |
| 2 | `max-age=86400` | Когда `certbot renew --dry-run` проходит |
| 3 | `max-age=31536000; includeSubDomains` | После хотя бы одного автопродления вживую |

`includeSubDomains` добавлять только тогда, когда HTTPS есть на **всех** поддоменах,
включая служебные. Иначе внутренний поддомен без сертификата перестанет открываться.

Про `preload` (список, встроенный в сами браузеры) — одно: попадание в него
необратимо в разумные сроки, без уверенности в инфраструктуре туда лучше не подаваться.

**Откат HSTS:** снизить `max-age` до `0`, перезагрузить nginx и подождать, пока у
пользователей истечёт ранее выданный срок. Мгновенного отката нет — в этом и причина
осторожности.

## Caddy — вариант, где TLS настраивается сам

Caddy получает и продлевает сертификат самостоятельно, без certbot и таймеров.
Минимальный рабочий файл:

```
ваш-домен.ru {
    root * /var/www/site
    file_server
}
```

Этого достаточно: сертификат выпустится при первом запуске, http сам будет
перенаправляться на https, продление пойдёт фоном. Для проекта без исторического
конфига nginx это заметно меньше мест, где можно ошибиться. Готовый файл с
заголовками — `templates/Caddyfile-security`.

## ⚠️ Отключённая проверка сертификата в коде

Строки, которые полностью обесценивают всё вышенастроенное: `verify=False` (Python),
`rejectUnauthorized: false` (Node.js), `InsecureSkipVerify: true` (Go),
`curl -k` в shell-скриптах.

Каждая означает: «соединяйся, не проверяя, с кем именно». Шифрование остаётся, но
защита от подмены исчезает — а это и была основная ценность. Появляются такие строки
обычно при отладке («не работает на локальном сертификате») и остаются в боевом коде.

Найти:

```bash
grep -rn -E 'verify\s*=\s*False|rejectUnauthorized|InsecureSkipVerify|curl .*-k ' . \
  --exclude-dir=node_modules --exclude-dir=.git
```

Правильное решение — не отключать проверку, а добавить нужный корневой сертификат в
доверенные на той машине, где идёт разработка.

## Мониторинг срока

Автопродление ломается тихо: истёкший hook, изменившийся путь, закрытый 80 порт.
Поэтому нужна внешняя проверка:

```bash
echo | openssl s_client -servername ваш-домен.ru -connect ваш-домен.ru:443 2>/dev/null \
  | openssl x509 -noout -enddate
```

Поставить её в cron с письмом при остатке меньше 20 дней или подключить любой внешний
мониторинг, следящий за сроком сертификата. Подробнее — `updates-and-logs.md`.
