# Заголовки безопасности и CSP

---

Заголовки — несколько строк, которые сервер добавляет к каждому ответу. Браузер их
читает и меняет своё поведение. Настройка бесплатная, кода не касается и почти ничего
не ломает — кроме CSP, которому здесь отведена большая половина страницы.

В nginx они добавляются директивой `add_header` с ключевым словом `always` в конце.
Без `always` заголовок не попадёт в ответы с кодами ошибок — то есть ровно туда, где он
чаще всего и нужен.

⚠️ Особенность nginx: `add_header` внутри `location` **отменяет все** `add_header`
уровня `server`. Не дополняет, а заменяет целиком. Поэтому если в каком-то `location`
добавляется свой заголовок, там придётся перечислить и все остальные. В шаблоне
`templates/nginx-security.conf` это учтено.

## Заголовки по одному

### Strict-Transport-Security

Браузер запоминает: на этот сайт — только по защищённому соединению. Даже если человек
наберёт адрес без `https`, браузер сам исправит его ещё до отправки запроса.

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
```

**Нет его:** самый первый запрос уходит по http, и его можно перехватить и увести на
подделку — редирект на https тут не поможет, перехват происходит раньше.
⚠️ Значение `max-age` наращивается постепенно. Подробно и с таблицей — `tls.md`.

### X-Content-Type-Options

```nginx
add_header X-Content-Type-Options "nosniff" always;
```

Браузер перестаёт угадывать тип файла по содержимому и верит тому, что сказал сервер.

**Нет его:** файл, загруженный пользователем как «картинка», внутри которого лежит код,
может быть распознан браузером как скрипт и выполнен. Важно там, куда загружают файлы.

### Referrer-Policy

```nginx
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

Когда со страницы переходят на чужой сайт, браузер обычно сообщает ему полный адрес, с
которого пришли. В адресе бывают номера заказов, идентификаторы клиентов, иногда токены.
Это значение оставляет чужим сайтам только имя домена.

**Нет его:** любой внешний сервис — картинка, счётчик, ссылка — узнаёт адреса ваших
внутренних страниц.

### Permissions-Policy

```nginx
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
```

Пустые скобки значат «никому». Страница физически не может запросить камеру, микрофон
и местоположение — даже чужой скрипт, если он туда попал.

**Нет его:** запрос доступа остаётся возможным. Он показывает пользователю окно
подтверждения, но это окно легко принять за системное.

### X-Frame-Options и frame-ancestors

```nginx
add_header X-Frame-Options "DENY" always;   # и в CSP: frame-ancestors 'none'
```

Оба запрещают встраивать ваш сайт в чужую страницу. `X-Frame-Options` — старый
заголовок, `frame-ancestors` внутри CSP — современный: он умеет больше, например
разрешить встраивание только своим доменам. При наличии обоих браузер слушает
`frame-ancestors`, старый оставляют для совместимости.

**Нет их:** вашу страницу открывают внутри прозрачного слоя на чужом сайте, поверх
рисуют свои элементы — человек думает, что нажимает кнопку одного сайта, а нажимает
кнопку вашего.

### server_tokens off и X-Powered-By

```nginx
server_tokens off;                  # в блоке http или server
proxy_hide_header X-Powered-By;     # если бэкенд его добавляет
```

`Server: nginx/1.18.0` и `X-Powered-By: PHP/7.4` — это подсказка сканеру: версия
известна, дальше подбирается готовый эксплойт под неё.

**Нет их:** не уязвимость сама по себе, но бесплатно закрываемая подсказка. Полностью
убрать строку `Server` штатный nginx не умеет — он оставит `Server: nginx` без версии,
и этого достаточно.

## Content-Security-Policy

### Из чего состоит

CSP — список правил вида «что откуда разрешено грузить», записанный одной строкой:
`имя-директивы источник1 источник2; имя-директивы источник; …`. Директивы разделяются
точкой с запятой, источники внутри директивы — пробелами.

| Источник | Что значит |
|---|---|
| `'self'` | Только ваш собственный домен |
| `'none'` | Ничего и ниоткуда |
| `https://пример.ru` | Конкретный домен |
| `https://*.пример.ru` | Любой его поддомен |
| `data:` | Содержимое, вписанное прямо в адрес (обычно мелкие картинки и шрифты) |
| `blob:` | Данные, созданные самой страницей в памяти браузера |

### Разбор реального CSP построчно

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob: https://*.виджет.ru; font-src 'self';
connect-src 'self' https://*.виджет.ru; worker-src 'self'; manifest-src 'self';
frame-src https://*.виджет.ru; frame-ancestors 'none';
base-uri 'self'; form-action 'self'
```

| Строка | Что разрешает |
|---|---|
| `default-src 'self'` | Значение по умолчанию для всего, что не указано отдельно: только свой домен |
| `script-src 'self'` | Код грузится только со своего домена. Главная строка всей политики |
| `style-src` | Оформление. `'unsafe-inline'` — вынужденная уступка, см. ниже |
| `img-src` | Картинки: свои, вписанные в адрес, созданные страницей, и картинки виджета |
| `font-src 'self'` | Шрифты только свои — сторонние сервисы шрифтов не подключаются |
| `connect-src` | Куда страница может отправлять запросы: свой сервер и сервер виджета |
| `worker-src` | Фоновые обработчики, включая офлайн-режим |
| `manifest-src` | Файл описания приложения (иконки, имя при установке на телефон) |
| `frame-src` | Кого можно встроить **внутрь** страницы |
| `frame-ancestors 'none'` | Кто может встроить **вашу** страницу. Никто |
| `base-uri 'self'` | Нельзя подменить базовый адрес и увести загрузку всех скриптов |
| `form-action 'self'` | Формы отправляются только на ваш сервер, а не на чужой |

Две последние строки пропускают чаще всего, а они закрывают приёмы в обход `script-src`.

### Чем плохи unsafe-inline и unsafe-eval

`script-src 'unsafe-inline'` разрешает выполнять код, написанный прямо в тексте
страницы. Проблема в том, что именно так выглядит и вставленный чужой код: браузер не
отличает ваш встроенный скрипт от чужого. С этой строкой CSP как защита от вставки
кода почти перестаёт работать — это первое, что нужно убирать.

`script-src 'unsafe-eval'` разрешает выполнять строки как код. Позволяет превратить
любую строку, пришедшую с сервера или из формы, в исполняемую программу.

`style-src 'unsafe-inline'` — намного мягче: это про оформление, а не про код. Многие
сборщики фронтенда без него не работают, поэтому оставить его — распространённый и
приемлемый компромисс. `unsafe-inline` **в script-src** — нет.

## ⚠️ Безопасное внедрение CSP

CSP — единственный заголовок из этого списка, который реально ломает работающие сайты.
Включённый сразу в бою, он выключает часть скриптов молча: страница открывается,
но кнопка не нажимается и данные не грузятся, а в логах сервера всё в порядке.

Порядок, который снимает риск:

**Шаг 1. Включить режим отчёта.** Заголовок с другим именем — браузер только пишет
нарушения в консоль, ничего не блокируя:

```nginx
add_header Content-Security-Policy-Report-Only "default-src 'self'; script-src 'self'; …" always;
```

**Шаг 2. Собрать нарушения.** Пройти по всем разделам сайта — главная, вход, списки,
формы, загрузка файлов, печать, экспорт — с открытой консолью браузера (F12). Каждое
сообщение `Refused to load …` — то, что сломалось бы в боевом режиме. Обойти нужно
именно все разделы: редкая страница экспорта ломается так же легко, как главная.

**Шаг 3. Починить код, а не политику.** Разбор каждого нарушения — ниже.

**Шаг 4.** Когда консоль чистая — заменить имя `Content-Security-Policy-Report-Only`
на боевое `Content-Security-Policy`.

**Откат:** вернуть имя `…-Report-Only`, `nginx -t && systemctl reload nginx`. Действует
немедленно, у пользователей ничего не запоминается — в отличие от HSTS. Именно поэтому
CSP безопаснее HSTS в смысле отката, но опаснее в смысле немедленного эффекта.

### Типовые поломки и как чинить правильно

| Что ломается | Сообщение в консоли | Правильное решение | Неправильное |
|---|---|---|---|
| Шрифты, встроенные сборщиком как `data:`-строки | `Refused to load the font` | Добавить `font-src 'self' data:` — это безопасно, шрифт кодом не является | `default-src *` |
| Инлайновые стили из сборщика | `Refused to apply inline style` | `style-src 'self' 'unsafe-inline'` — приемлемо | Ставить `unsafe-inline` ещё и в `script-src` |
| Свой встроенный `<script>` в HTML | `Refused to execute inline script` | Вынести код в отдельный `.js`-файл | `script-src 'unsafe-inline'` |
| Сторонний виджет (чат, мессенджер) | `Refused to connect` / `frame` | Перечислить его домены в `script-src`, `connect-src`, `frame-src` | Разрешить `https:` целиком |
| Карты | `Refused to load` для картинок и запросов | Домены карт в `img-src` и `connect-src` | `img-src *` |
| Метрика и счётчики | `Refused to load the script` | Домен счётчика в `script-src` и `connect-src` | `unsafe-inline` |
| Картинки, созданные страницей (печать, превью) | `Refused to load the image` | `img-src 'self' blob:` | `img-src *` |

Общее правило: политика расширяется **конкретным доменом под конкретную директиву**.
Замена `script-src 'self'` на `script-src *` формально убирает сообщение из консоли, но
после этого заголовок остаётся только для вида — проверяющий увидит CSP, а защиты уже
нет.

Отдельно про сторонние виджеты: подключая чужой скрипт, вы даёте ему те же права, что
и своему коду. CSP ограничивает, откуда он загружен, но не то, что он делает внутри
страницы. Поэтому перед добавлением домена в `script-src` стоит один раз спросить,
нужен ли этот виджет вообще.

## Проверка результата

```bash
curl -sSI https://ваш-домен.ru/ | grep -iE 'security|x-content|referrer|permissions|frame|server'
```

И отдельно — консоль браузера на живом сайте: заголовок может присутствовать и при
этом блокировать половину функций.
