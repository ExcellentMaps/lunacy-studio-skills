# Guard Server — периметр, сервер и секреты

Слои 1 и частично 5. Отвечает на вопрос: **что вообще видно снаружи и как это защищено**.

## Главный принцип

> **Наружу смотрит ровно одна дверь. Всё остальное слушает только себя.**

Одна дверь — веб-сервер на 443 порту. База данных, админ-панели, служебные API, метрики,
очереди — всё это слушает `127.0.0.1` и доступно только самому серверу. Не «защищено
паролем», а именно **недоступно из интернета**.

Почему это важнее всего остального: сервис, недоступный снаружи, нельзя взломать снаружи,
какой бы дырявый он ни был. Сервис, открытый в интернет, находят сканеры за минуты после
запуска — не потому что кто-то нацелился, а потому что весь диапазон адресов сканируется
непрерывно.

---

## ⚠️ Перед любой работой с firewall и SSH

**Откройте вторую сессию на сервер и не закрывайте её.**

Первая — рабочая, в ней вы вносите изменения. Вторая — спасательная. Если правило отрежет
SSH, рабочая сессия умрёт, а спасательная останется живой и позволит откатить. Без второй
сессии единственный путь назад — консоль в панели хостинга, а она есть не везде и не всегда
работает так, как хочется в три часа ночи.

Дополнительно, если панель хостинга умеет снапшоты — сделать снапшот перед началом.

## Порядок работы

### Шаг 1. Посмотреть, что открыто

Не меняя ничего:

- какие порты слушают и на каком адресе (`0.0.0.0` — наружу, `127.0.0.1` — только себе);
- что видно снаружи (проверка с другой машины, а не с самого сервера);
- состояние firewall;
- есть ли HTTPS и когда истекает сертификат;
- какие заголовки отдаёт сайт;
- где лежат секреты и какие у файла права;
- открыт ли вход по SSH с паролем.

Готовые команды — в `references/recon.md`.

Важная тонкость: **Docker умеет обходить ufw.** Проброшенный порт контейнера может быть
доступен снаружи, даже когда ufw показывает, что всё закрыто — Docker пишет свои правила
в iptables мимо ufw. Проверять надо снаружи, а не по выводу `ufw status`.

## Заголовки безопасности: минимальный набор

Готовый конфиг — `templates/nginx-security.conf` (nginx) и `templates/Caddyfile-security`
(Caddy). Что каждый заголовок делает, человеческим языком:

| Заголовок | Что делает простыми словами |
|---|---|
| `Strict-Transport-Security` | Браузер запоминает: на этот сайт только по защищённому соединению. Даже если человек наберёт адрес без `https`, подслушать первый запрос не выйдет |
| `Content-Security-Policy` | Список того, откуда странице разрешено грузить код и картинки. Чужой скрипт, вставленный в страницу, просто не запустится |
| `X-Content-Type-Options: nosniff` | Браузер не пытается угадать тип файла. Загруженная «картинка», внутри которой код, не выполнится |
| `Referrer-Policy` | Чужие сайты не узнают, с какой именно страницы к ним пришли — в адресе бывают номера заказов и токены |
| `Permissions-Policy` | Страница не может запросить камеру, микрофон и геолокацию |
| `frame-ancestors 'none'` | Сайт нельзя встроить в чужую страницу (защита от подмены интерфейса) |

**CSP — единственный заголовок, который реально ломает сайты.** Порядок внедрения:
сначала в режиме отчёта (`Content-Security-Policy-Report-Only`), посмотреть, что бы
сломалось, потом включать боевой. Подробно — `references/headers-and-csp.md`.

## Секреты: три правила

1. **Не в git.** Никогда, ни в каком виде, даже «временно». Git помнит всё: удалить файл
   следующим коммитом недостаточно, он остаётся в истории.
2. **Права `600` и владелец root.** Файл с ключами читает только тот, кому положено.
3. **Утёк — считается скомпрометированным.** Не «наверное никто не заметил», а ротация:
   выпустить новый, обновить везде, отозвать старый. Ключ, который полежал в публичном
   репозитории пять минут, уже собран ботами — они сканируют GitHub непрерывно.

Что делать, если секрет уже попал в git, — `references/secrets.md`.

## Что объяснить владельцу

**Закрытые служебные порты.**
База данных и служебные сервисы доступны только самому серверу — из интернета к ним не
подключиться вообще. Без этого автоматические сканеры находят открытую базу в течение
часа после запуска и начинают подбирать пароль круглосуточно.

**HTTPS.**
Соединение шифруется: замочек в адресной строке. Никто между сотрудником и сервером —
ни владелец кафейного Wi-Fi, ни провайдер — не видит ни паролей, ни данных клиентов.
Сертификат продлевается автоматически, вручную ничего делать не нужно.

**Ограничение частоты запросов.**
С одного адреса принимается разумное количество запросов в секунду. Обычная работа в
этот лимит не упирается никогда, а программа, перебирающая пароли или выкачивающая базу,
упирается сразу.

**Защита SSH.**
Вход на сервер только по ключу — файлу, который есть у вас и которого нет ни у кого
другого. Пароль подобрать можно, ключ — нет. Плюс автоматическая блокировка адресов,
с которых пытаются ломиться.

## Частые ошибки

- **Проверка открытых портов с самого сервера.** Изнутри видно всё; надо снаружи.
- **Docker в обход ufw.** Порт проброшен как `-p 5432:5432` — он открыт в интернет,
  что бы ни показывал ufw. Правильно: `-p 127.0.0.1:5432:5432`.
- **CSP, включённый сразу в бою.** Половина сайта перестаёт работать в пятницу вечером.
- **`ufw enable` без разрешённого SSH.** Мгновенная потеря доступа к серверу.
- **Сертификат без автопродления.** Через 90 дней сайт встречает клиентов красным
  предупреждением браузера.
- **`.env` в корне сайта.** Файл отдаётся веб-сервером как обычный текст — все ключи
  открыты по прямой ссылке.
- **Логи с персональными данными без ротации.** Диск кончается, а заодно накапливается
  база данных в открытом виде.
