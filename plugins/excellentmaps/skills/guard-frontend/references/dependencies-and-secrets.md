# Зависимости и секреты во фронтенде

чужой код, который вы установили, и ваш ключ, который уехал в браузер вместе

## Часть 1. Зависимости

В типичном фронтенд-проекте свой код — несколько процентов от общего объёма.
Остальное — чужие библиотеки и библиотеки этих библиотек. Все они выполняются
с теми же правами, что и ваш код.

### Lock-файл обязан быть в git

`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml` — файл, который фиксирует точные
версии всего дерева зависимостей, включая вложенные.

Без него `npm install` на сервере сборки может поставить не то, что стояло у вас:
версии обновились, и в проект приехал код, который никто не видел. Проверено у вас,
собрано на сервере другое.

```bash
git check-ignore -v package-lock.json     # если файл найден в .gitignore — это ошибка
npm ci                                    # ci, а не install: ставит строго по lock-файлу
```

На сервере сборки — всегда `npm ci`. Он не меняет lock-файл и падает, если тот
разошёлся с `package.json`. Это нужное поведение.

### Проверка уязвимостей

```bash
# только то, что уезжает в бой; dev-зависимости отдельно
npm audit --omit=dev

# осмысленная детализация
npm audit --omit=dev --json > audit.json

# второй инструмент, независимый от npm, работает по lock-файлу
osv-scanner --lockfile=package-lock.json
```

Два инструмента, потому что базы у них разные: `npm audit` смотрит в базу npm,
`osv-scanner` — в открытую базу OSV. Совпадение находок — хороший знак, расхождение —
повод посмотреть внимательнее.

Запускать регулярно, а не однократно перед сдачей: уязвимость публикуют не тогда,
когда вам удобно. Разумно повесить на сборку.

### Как читать результат и не утонуть

Первый запуск `npm audit` в живом проекте выдаёт десятки строк со словом `high`.
Бросаться чинить всё подряд — верный способ потратить неделю и сломать сборку.

Два вопроса к каждой находке, в этом порядке:

| Вопрос | Если «нет» |
|---|---|
| **1. Вызывается ли уязвимая функция в вашем коде?** Уязвимость обычно в конкретном методе конкретного модуля. Часто пакет стоит ради другой его части | Приоритет падает. Обновить при случае, а не ночью |
| **2. Пакет боевой или только для сборки?** Уязвимость в `devDependencies` (сборщик, линтер, тестовый прогон) не уезжает к пользователю | Приоритет падает. Опасность в основном для вашей машины и сервера сборки |

🔴 Чинится первым: пакет из боевой сборки, уязвимая функция которого реально
вызывается, и уязвимость даёт выполнение кода или обход проверки прав.

🟡 Откладывается: `devDependencies`, отказ в обслуживании в утилите сборки,
уязвимость в неиспользуемой части пакета.

Порядок действий по находке:

```bash
npm ls имя-пакета          # понять, кто его тянет: вы напрямую или чужая библиотека
npm audit fix              # безопасные обновления в рамках совместимых версий
npm audit fix --force      # ⚠️ ломает совместимость. Только вручную и с прогоном тестов
```

⚠️ `npm audit fix --force` может поднять мажорную версию и тихо сломать работающую
функцию. После него обязателен прогон приложения, а не только сборки.

Если уязвимость в пакете, который тянет чужая библиотека, а обновления нет — вариантов
три: обновить родительскую библиотеку, заменить её, либо зафиксировать решение
«принимаем риск» письменно, с датой и причиной. Третий вариант законен, если он
осознанный, а не молчаливый.

### Новая зависимость — решение, а не рефлекс

Прежде чем поставить пакет ради одной функции:

- Сколько он тянет за собой? `npm info имя dependencies`.
- Когда было последнее обновление и сколько открытых проблем?
- Это одна функция на 20 строк, которую проще написать самому?
- Нужен ли он в бою или только при сборке?

Каждый установленный пакет — это доверие незнакомому человеку, выданное навсегда
и без пересмотра.

### Атака на цепочку поставок

Простыми словами: злоумышленник не ломает ваш сайт. Он получает контроль над
маленькой библиотекой, которую вы установили пять лет назад и с тех пор не вспоминали,
и добавляет в неё пару строк. Вы обновляете зависимости — и эти строки приезжают
в вашу сборку сами, с вашего же согласия.

Способы получить контроль бывают разные: аккаунт автора угнали, автор устал
и передал проект «доброму помощнику», имя пакета похоже на популярное на одну букву.

Что снижает риск:

- lock-файл и `npm ci` — вы ставите ровно проверенное, а не «самое свежее»;
- меньше зависимостей — меньше площадь;
- 🟠 осторожность с `postinstall`-скриптами: они выполняются при установке, до любой
  проверки. Для сборочных окружений имеет смысл `npm ci --ignore-scripts`, если проект
  это переживает;
- обновление осознанными порциями, а не «обновим всё разом перед релизом».

## Часть 2. Секреты

### ⚠️ Во фронтенде не бывает секретов

Всё, что попало в браузер, известно. Код, адреса API, ключи, логика проверок,
скрытые поля формы, закомментированные куски — всё открывается по F12 и сохраняется
одной кнопкой. Минификация и обфускация этого не меняют (см. `мифы.md`).

Практическое следствие:

- если ключ нужен браузеру — он **публичный** и должен быть безопасен сам по себе;
- если ключ должен быть тайным — он живёт на сервере, а браузер обращается к вашему
  серверу, который уже ходит к сервису.

Отдельная ловушка сборщиков: переменные окружения с публичным префиксом (`VITE_`,
`NEXT_PUBLIC_`, `REACT_APP_`) **подставляются прямо в текст сборки**. `.env` в
`.gitignore` создаёт ощущение, что значение спрятано, — оно не спрятано, оно в `dist/`.

### Что делать, если ключ попал в сборку

Порядок важен. Он именно такой, а не обратный:

| # | Действие | Почему в этом порядке |
|---|---|---|
| 1 | **Ротировать ключ**: выпустить новый в панели сервиса, старый отозвать | Ключ уже опубликован. Пока он жив, всё остальное бессмысленно |
| 2 | Проверить журнал сервиса: что делали этим ключом | Утечка могла быть использована. Это надо знать до разговора с владельцем |
| 3 | Убрать ключ из кода, перенести обращение на сервер | Чтобы не повторилось |
| 4 | Пересобрать и выложить | Старая сборка может лежать в кеше CDN |
| 5 | Почистить историю git, если ключ коммитили | История публична для всех, у кого есть доступ к репозиторию |

🔴 Частая ошибка — начать с пункта 3 или 5. «Сначала аккуратно уберём из кода, потом
разберёмся с ключом». Между этими двумя действиями проходят дни, и всё это время
рабочий ключ лежит в открытом доступе. Чистка истории без ротации не даёт ничего:
ключ уже скачан тем, кто его нашёл.

Пункт 5 делается после ротации и осознанно: переписывание истории ломает работу
у всех, кто уже склонировал репозиторий.

### Публичный ключ в коде — это нормально

Некоторые сервисы устроены так, что браузеру выдаётся ключ, который **и должен**
быть виден: публичный ключ платёжной формы, анонимный ключ базы данных, идентификатор
карт или аналитики. Он не тайна по замыслу.

Опасно не то, что он виден. Опасно то, **что ему разрешено на стороне сервиса**.

| Ситуация | Оценка |
|---|---|
| Публичный ключ виден, а правила доступа в базе разрешают читать только свои записи | 🟡 Нормально. Так и задумано |
| Публичный ключ виден, а правила доступа не настроены — по нему читается вся база | 🔴 Красный уровень. Утечка базы, а не «утечка ключа» |
| В коде служебный ключ с полными правами (`service_role`, `secret`, `admin`) | 🔴 Красный. Немедленная ротация |

Отсюда правило: находка «ключ в коде фронтенда» **не оценивается во фронтенде**.
Она отправляется в `guard-data` — там проверяется, что этому ключу разрешено.
Ответ «ключ публичный, всё в порядке» имеет право на существование только после
этой проверки, а не вместо неё.

### Ещё две мелочи, которые дороже, чем кажутся

**Карты исходников (`sourcemap`) в бою.** Они восстанавливают исходный код со всеми
именами, комментариями и структурой. Полезно для отладки, не нужно публике.

```js
build: { sourcemap: false }     // vite
```

Если карты нужны для сервиса отчётов об ошибках — их загружают в этот сервис
отдельно и не выкладывают рядом со сборкой.

**`console.log` в бою.** В консоль обычно пишут именно то, что отлаживали: ответы
API целиком, токены, данные клиентов. Вычищается настройкой сборки:

```js
esbuild: { drop: ['console', 'debugger'] }     // vite, только для build
```

Так это сделано в `vite.config.ts` разбираемого проекта — вместе с `sourcemap: false`.
Обе настройки стоят копейки и закрывают целый класс случайных утечек.
