# CSP со стороны кода

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

Content-Security-Policy — это список того, откуда странице разрешено брать код,
стили, картинки и шрифты. Браузер выполняет только разрешённое, всё остальное молча
отклоняет.

Сам заголовок ставится на сервере — это `guard-server`. Здесь про другое: **что надо
поправить в коде**, чтобы строгий CSP можно было включить и не пришлось добавлять
`'unsafe-inline'`, который отменяет половину смысла.

---

## Зачем это нужно

CSP — вторая линия после правильного вывода данных. Если чужой код всё-таки оказался
на странице, строгая политика не даёт ему выполниться, а если он выполнился — не даёт
отправить украденное на чужой сервер.

Ориентир для закрытой системы:

```
default-src 'self';
script-src 'self';
style-src 'self';
img-src 'self' data:;
font-src 'self';
connect-src 'self' https://api.ваш-домен;
frame-ancestors 'none';
base-uri 'self';
form-action 'self';
object-src 'none'
```

Слово `'self'` означает «только мой домен». Как только появляется
`script-src 'unsafe-inline'`, защита от XSS практически исчезает: именно inline-код
и внедряет злоумышленник.

## Что чинить в коде

### 1. Inline-обработчики в разметке

```html
<!-- было -->
<button onclick="удалитьКлиента(12)">Удалить</button>
<a href="javascript:void(0)" onclick="открыть()">Подробнее</a>
```

```html
<!-- стало -->
<button id="del" data-id="12">Удалить</button>
```

```js
document.getElementById('del')
  .addEventListener('click', (e) => удалитьКлиента(e.currentTarget.dataset.id))
```

Во фреймворках это обычно уже так: `onClick={...}` в React и `@click` в Vue — не
inline-атрибуты в итоговой разметке, а обработчики, которые фреймворк навешивает
кодом. Проблема живёт в старых страницах, серверных шаблонах, письмах и виджетах.

```bash
rg -n "on(click|change|load|error|submit|mouseover)=\"" src/ public/ templates/
rg -n "javascript:void" src/ public/
```

### 2. Inline-стили и `<style>` в разметке

`style-src 'self'` запрещает и `<style>` внутри страницы, и атрибут `style="..."`.

Варианты:

| Вариант | Когда подходит |
|---|---|
| Вынести в CSS-файл | Всегда, когда стиль статичен |
| CSS-переменные: в атрибуте только значение, правило в файле | Динамические цвета, ширина прогресс-бара |
| `nonce` на теге `<style>` | Когда стиль генерируется сервером на каждый запрос |
| `'unsafe-inline'` для `style-src` | Компромисс. Менее опасен, чем для скриптов, но это всё же уступка |

Приём с переменной:

```css
.progress { width: var(--w, 0%); }
```

```jsx
<div className="progress" style={{ '--w': `${процент}%` }} />
```

⚠️ Многие UI-библиотеки (анимации, всплывающие подсказки, виртуальные списки)
ставят inline-стили сами. Это выясняется только на практике — поэтому режим отчётов
ниже обязателен.

### 3. `nonce` и `hash` — если inline всё-таки нужен

`nonce` — случайное число, которое сервер генерирует **на каждый запрос**, кладёт
в заголовок CSP и в атрибут тега. Браузер выполняет только тег с совпавшим значением.

```
Content-Security-Policy: script-src 'self' 'nonce-r4nd0m2024';
```

```html
<script nonce="r4nd0m2024">/* этот выполнится */</script>
```

🔴 Обязательное условие: nonce **новый на каждый ответ**. Постоянное значение,
зашитое в сборку, не даёт ничего — его прочитает любой.

`hash` — контрольная сумма неизменного скрипта; ломается при любой его правке.

### 4. `eval` и `new Function`

`script-src 'self'` запрещает и то и другое. Заодно запрещает `setTimeout('код', 100)`
со строкой вместо функции.

```bash
rg -n "\beval\(|new Function\(|setTimeout\(\s*['\"]|setInterval\(\s*['\"]" src/
```

Обычно встречается в трёх местах: разбор JSON «по старинке» (заменяется
`JSON.parse`), шаблонизаторы с компиляцией на лету, калькуляторы формул. Если
библиотека требует `'unsafe-eval'` — это повод искать замену, а не расширять политику.

## ⚠️ Ловушка, на которой спотыкаются почти все: встроенные ассеты

Сборщики по умолчанию встраивают мелкие файлы прямо в результат как `data:`-строки —
это экономит запросы. Мелкий шрифт, иконка, фоновая картинка превращаются в длинную
строку внутри CSS.

А политика `font-src 'self'` разрешает шрифты **только файлами со своего домена**.
Встроенный шрифт — это `data:`, и браузер его блокирует.

Как это выглядит: сайт работает, вёрстка на месте, но текст показан системным
шрифтом вместо фирменного. Ошибки в интерфейсе нет, в консоли — сообщение о нарушении
CSP, которое никто не открывал. Проблему обычно ищут в путях к шрифтам и в кеше.

Два способа:

**Отключить встраивание** (предпочтительно — политика остаётся строгой):

```ts
// vite.config.ts
build: {
  assetsInlineLimit: 0,   // все ассеты становятся обычными файлами рядом со сборкой
}
```

Именно так решено в `vite.config.ts` разбираемого проекта — с комментарием прямо
в коде, чтобы следующий человек не вернул настройку обратно.

**Разрешить `data:` для конкретного типа** — уступка, приемлемая для картинок
(`img-src 'self' data:`) и нежелательная для шрифтов и скриптов.

## Сторонние виджеты, карты и метрики

Каждый внешний сервис требует внести свои домены в политику — и это хорошая точка
для разговора «а нужен ли он вообще».

| Что подключено | Что придётся разрешить |
|---|---|
| Карта | `script-src`, `img-src`, `connect-src`, часто `frame-src` домена карт |
| Чат поддержки | те же плюс `connect-src` для веб-сокета (`wss://`) |
| Счётчик посещений | `script-src`, `img-src`, `connect-src` |
| Видео | `frame-src` |

Два правила: перечислять **конкретные домены**, а не `https:` целиком; ничего
не разрешать «на всякий случай» — если в политике есть запись, а виджет давно
удалён, запись убирается.

Разбор рисков сторонних скриптов — `файлы-и-виджеты.md`.

## Отчёты о нарушениях

Браузер умеет сообщать, что он заблокировал, — по адресу, который вы укажете.

```
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report;
```

Обработчик на сервере принимает `POST` с телом в JSON и пишет его в журнал. Нужный
минимум полей: `blocked-uri` (что заблокировано), `violated-directive` (какое
правило), `document-uri` (на какой странице). Запись стоит ограничить по частоте:
страница с ошибкой генерирует тысячи отчётов в минуту, а расширения браузера создают
шум, к вашему коду отношения не имеющий.

## Порядок внедрения

Единственный порядок, который не ломает боевой сайт:

| Шаг | Что делаем | Сколько держим |
|---|---|---|
| 1 | Включить `Content-Security-Policy-Report-Only` с целевой строгой политикой. Сайт работает как раньше, браузер только сообщает о нарушениях | — |
| 2 | Собрать нарушения в журнал, походив по всем разделам системы во всех ролях | несколько дней реальной работы |
| 3 | Разобрать список: часть — свой код (чинить), часть — нужные внешние домены (внести в политику), часть — расширения браузера (игнорировать) | — |
| 4 | Починить код: inline-обработчики, стили, `eval`, встроенные ассеты | — |
| 5 | Повторить шаг 2. Отчётов быть не должно | — |
| 6 | Переключить заголовок на боевой `Content-Security-Policy` | — |
| 7 | Не забыть оставить `report-uri` — чтобы новые нарушения были видны | постоянно |

🟠 Шаг 2 нельзя сокращать. Редкие экраны — печать документа, экспорт, старый отчёт,
раздел администратора — открывают раз в месяц, и именно они ломаются после включения.

⚠️ Типовая ошибка — включить строгий CSP сразу, увидеть белый экран, добавить
`'unsafe-inline' 'unsafe-eval'` и решить, что CSP настроен. Такая политика
существует, но не защищает.

Проверка итогового заголовка — `guard-audit`, блок 3.
