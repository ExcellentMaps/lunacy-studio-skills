## Заход 1. Где данные попадают в DOM

Ищем места, где текст, введённый человеком или пришедший из базы, вставляется
в страницу **как разметка**, а не как текст. Это будущие точки XSS.

```bash
# универсальный поиск (ripgrep; если его нет — grep -rn)
rg -n "innerHTML|outerHTML|insertAdjacentHTML|document\.write" src/

# React
rg -n "dangerouslySetInnerHTML" src/

# Vue
rg -n "v-html" src/

# Angular
rg -n "bypassSecurityTrust|innerHTML" src/

# Svelte
rg -n '\{@html' src/

# шаблонизаторы: «тройные усы» и отключённое экранирование
rg -n '\{\{\{|\| *raw|\| *safe|escape *= *false' src/ templates/ views/
```

Отдельно — ссылки, адрес которых приходит из базы. Их редко считают опасными:

```bash
rg -n 'href=\{|href="\{\{|:href|\[href\]' src/
rg -n 'window\.open|location\.href *=|location\.assign' src/
```

Что записать по каждой находке: файл, строка, **откуда приходит значение**. Если
значение — константа из кода, это не проблема. Если оно пришло из поля ввода, из базы,
из адреса страницы или из ответа внешнего сервиса — это кандидат на разбор
в `xss-и-вывод.md`.

## Заход 2. Что лежит в браузере сотрудника

Смотреть глазами, а не по коду: код может класть одно, а реальность оказаться другой.

**DevTools → вкладка Application** (в русской версии Chrome — «Приложение»),
левая колонка:

| Раздел | Что смотреть |
|---|---|
| Local Storage → ваш домен | Каждый ключ. Есть ли токены, телефоны, имена клиентов, суммы |
| Session Storage | То же самое |
| Cookies → ваш домен | Таблица кук и их флаги (см. заход 5) |
| IndexedDB | Часто забытый кеш: там оседают целые списки клиентов |
| Cache Storage | Что закешировал Service Worker — ответы API туда попадают целиком |
| Service Workers | Есть ли он вообще и что кеширует |

Порядок действий:

1. Войти в систему под тестовым сотрудником.
2. Открыть несколько карточек клиентов, список, отчёт.
3. Открыть Application и просмотреть все шесть разделов.
4. Нажать «Выйти» и **повторить осмотр**. Всё, что осталось после выхода, увидит
   следующий человек за этим компьютером.

Тот же осмотр из консоли, если удобнее списком:

```js
Object.keys(localStorage)
Object.keys(sessionStorage)
document.cookie          // покажет только куки БЕЗ флага HttpOnly — это и есть проверка
```

🟠 Если `document.cookie` показывает куку сессии — значит, `HttpOnly` не выставлен.

## Заход 3. Что попало в собранные файлы

Собираем проект и ищем в результате то, чего там быть не должно.

```bash
npm run build          # получаем dist/

# ключи и пароли
rg -n -i "api[_-]?key|secret|passwd|password|private[_-]?key|bearer " dist/

# типовые форматы ключей сервисов
rg -n "sk_live_|sk_test_|AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{36}|xox[baprs]-" dist/

# токены вида JWT
rg -n -o "eyJ[A-Za-z0-9_-]{20,}" dist/ | head

# все внешние адреса, куда ходит фронтенд
rg -n -o "https?://[a-zA-Z0-9.-]+" dist/ | sed 's/.*http/http/' | sort -u

# карты исходников — в бою их быть не должно
find dist -name "*.map"

# служебные комментарии, которые забыли убрать
rg -n -i "TODO|FIXME|временно|захардкод|hack" dist/
```

⚠️ **Важная оговорка про обфускацию.** Если сборка обфусцирована с упаковкой строк
в массив и кодированием base64 (именно так настроен `vite.config.ts` в этом проекте),
обычный `rg` по `dist/` **не найдёт ничего** — строк в открытом виде там нет. Это не
доказательство отсутствия ключей, а доказательство того, что вы искали не в том файле.
Соберите без обфускации и ищите там:

```bash
NO_OBFUSCATE=1 npm run build
rg -n -i "api[_-]?key|secret|password" dist/
```

Отдельно проверьте файл переменных окружения: во фронтенд-сборках в бандл попадает
всё, что начинается с публичного префикса (`VITE_`, `NEXT_PUBLIC_`, `REACT_APP_`).

```bash
rg -n "VITE_|NEXT_PUBLIC_|REACT_APP_" .env* src/
```

Что делать с находками — `зависимости-и-секреты.md`, раздел про секреты. Коротко:
сначала ротация ключа, потом чистка кода.

## Заход 4. Какие чужие скрипты грузятся на странице

Каждый внешний скрипт выполняется с теми же правами, что и ваш собственный код.

**По коду:**

```bash
rg -n "<script[^>]*src=" index.html public/ dist/index.html
rg -n -i "googletagmanager|google-analytics|mc\.yandex|jivo|tawk|carrotquest|bitrix|hotjar|sentry" src/ index.html
rg -n "<iframe" src/ index.html
```

**По факту (надёжнее):** DevTools → Network → перезагрузить страницу → фильтр `JS`.
Правым щелчком по шапке таблицы включить колонку **Domain** и отсортировать по ней.
Всё, что не ваш домен — чужой код на вашей странице.

Выписать в таблицу:

| Домен | Что это | Кто поставил | Нужен ли |
|---|---|---|---|
| example-analytics.ru | счётчик посещений | маркетолог, 2023 | ? |

Разбор — `файлы-и-виджеты.md`.

## Заход 5. Флаги кук

DevTools → Application → Cookies → ваш домен. В таблице есть колонки `HttpOnly`,
`Secure`, `SameSite`, `Expires`. Смотреть надо именно на строку с кукой сессии.

| Колонка | Должно быть у куки сессии |
|---|---|
| HttpOnly | галочка стоит |
| Secure | галочка стоит |
| SameSite | `Lax` или `Strict` |
| Expires / Max-Age | ограничено, не «через 10 лет» |

Та же проверка снаружи, без браузера:

```bash
curl -sI https://ВАШ_ДОМЕН/ | grep -i "^set-cookie"
curl -sI https://ВАШ_ДОМЕН/ | grep -i "content-security-policy\|x-frame-options"
```

🔴 Кука сессии без `HttpOnly` — первое, что чинят. Почему именно она —
`хранилище-куки-csrf.md`.
