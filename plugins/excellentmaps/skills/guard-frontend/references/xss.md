# XSS и безопасный вывод данных

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

XSS — это когда текст, который ввёл человек, страница выполняет как программу.
Аббревиатура расшифровывается как «межсайтовый скриптинг», но расшифровка ничего
не объясняет. Объясняет пример.

---

## Пример из CRM

Менеджер открывает карточку клиента и в поле «Комментарий» пишет не «перезвонить
в четверг», а строку, которая выглядит как текст, но для браузера является командой.
Комментарий сохраняется в базу — это обычная работа системы, никакой ошибки здесь нет.

Через день карточку открывает руководитель. Его браузер получает комментарий с сервера
и вставляет в страницу. Если система вставляет его **как разметку**, браузер не видит
разницы между текстом менеджера и кодом программиста: он выполняет и то и другое.

С этого момента чужая команда работает в браузере руководителя и умеет ровно то же,
что и он сам:

- читать всё, что открыто на экране;
- отправлять запросы к серверу от его имени — система видит обычные действия
  авторизованного руководителя;
- забрать токен сессии, если тот лежит в месте, доступном коду страницы;
- тихо выгружать базу в фоне, пока человек работает.

Заметить это почти невозможно: внешне ничего не происходит.

## Три вида

| Вид | Где живёт чужой код | Пример в CRM |
|---|---|---|
| **Хранимый** | в базе, показывается всем, кто открыл запись | комментарий из примера выше, имя клиента, название компании, содержимое заявки с сайта |
| **Отражённый** | в адресе страницы, срабатывает у того, кто перешёл по ссылке | `?search=...` подставляется в заголовок «Результаты по запросу…», ссылку присылают сотруднику в мессенджере |
| **DOM** | вообще не доходит до сервера, всё происходит в браузере | скрипт страницы берёт кусок адреса после `#` и кладёт в `innerHTML` |

🔴 Для CRM опаснее всего **хранимый**: он один раз записан и потом срабатывает
у каждого, кто откроет запись, включая владельца с максимальными правами.

Отдельно стоит помнить, что данные приходят не только из полей ввода. Форма заявки
с сайта, входящий вебхук от мессенджера, импорт из Excel, ответ внешнего сервиса —
всё это тоже ввод, и он тоже попадает в карточку.

## Почему современные фреймворки защищают сами

React, Vue, Angular и Svelte по умолчанию вставляют значения **как текст**. Если
в переменной лежит разметка, на экране появятся просто угловые скобки — браузер
покажет их как символы, а не как команду. Это поведение по умолчанию, его не нужно
включать.

Поэтому XSS во фреймворковом проекте почти всегда находится там, где программист
**сознательно отключил** эту защиту — обычно ради форматирования: жирный текст
в описании, перенос строк, ссылка внутри комментария.

| Фреймворк | Чем отключают защиту | Что искать |
|---|---|---|
| React | `dangerouslySetInnerHTML={{ __html: x }}` | само название говорит; ищется грепом за секунду |
| Vue | `v-html="x"` | часто в описаниях товаров и шаблонах писем |
| Angular | `bypassSecurityTrustHtml()`, `[innerHTML]` | `DomSanitizer` вызывают, чтобы «починить», что он «ломает» |
| Svelte | `{@html x}` | — |
| Шаблонизаторы | `{{{ x }}}` (Handlebars), `\| raw` (Twig/Jinja), `\| safe`, `autoescape false` | серверные шаблоны писем и печатных форм |

Правило простое: **каждое такое место должно быть объяснимо**. Если рядом нет очистки
и нельзя ответить, откуда приходит значение, — это дыра.

## Ссылки из базы: `javascript:` в поле «Сайт клиента»

Отдельный случай, который не закрывается экранированием. Поле «Сайт клиента» —
обычный текст, он корректно вставляется в атрибут `href`. Но если менеджер вписал
туда адрес, начинающийся с `javascript:`, клик по ссылке выполнит команду.

То же относится к `data:text/html` и к ссылкам, которые ставит внешняя интеграция.

Проверять адрес перед выводом:

```js
function безопаснаяСсылка(значение = '') {
  try {
    const u = new URL(значение, window.location.origin)
    return ['http:', 'https:', 'mailto:', 'tel:'].includes(u.protocol) ? u.href : null
  } catch {
    return null                       // не разобралось — не ссылка
  }
}
```

Если функция вернула `null`, показываем текст без ссылки. Белый список протоколов —
именно белый: перечисляем разрешённые, а не пытаемся перечислить запрещённые.

Дополнительно для внешних ссылок: `rel="noopener noreferrer"` — иначе открытая
страница получает программный доступ к вкладке, из которой её открыли.

## Где разметка разрешена намеренно: письма и рассылки

Есть места, где HTML нужен по делу: шаблон письма клиенту, текст рассылки, описание
услуги с форматированием. Здесь нельзя просто экранировать — пропадёт смысл функции.

Здесь применяется **очистка** (sanitization): разметка разбирается, из неё оставляют
только разрешённые теги и атрибуты, всё остальное выбрасывается.

```js
import DOMPurify from 'dompurify'

const чисто = DOMPurify.sanitize(грязно, {
  ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'u', 'p', 'br', 'ul', 'ol', 'li', 'a', 'span'],
  ALLOWED_ATTR: ['href', 'title', 'target', 'rel'],
  ALLOWED_URI_REGEXP: /^(?:https?|mailto|tel):/i,
})
```

Три правила по очистке:

1. **Белый список, а не чёрный.** Перечисляем, что разрешено. Попытка перечислить
   запрещённое всегда неполна.
2. **Очищать при выводе, а не только при записи.** В базе уже могут лежать старые
   записи, записанные до того, как очистку добавили. И данные могут прийти мимо формы —
   через импорт или вебхук.
3. **Не писать свою очистку регулярными выражениями.** Это классическая ловушка:
   разметку нельзя надёжно разобрать регулярным выражением, а библиотеку поддерживают
   годами именно из-за потока обходов.

⚠️ Очистка на сервере и очистка в браузере — разные вещи. В браузере она нужна, чтобы
не выполнить чужой код у текущего сотрудника. На сервере — чтобы в базу не легло то,
что потом покажут в письме, в PDF или в другой системе, где никакой очистки нет.

## SVG — это тоже разметка

SVG-картинка внутри себя может содержать скрипт и обработчики событий. Поэтому:

- 🟠 SVG, загруженный пользователем, **нельзя вставлять в страницу как разметку**
  (inline). Показывать через `<img src="...">` — так скрипт внутри не выполняется.
- Логотип клиента, аватар, вложение в карточке — всё это потенциально SVG.
- Если inline-вставка нужна для перекраски иконок, вставлять так можно только **свои**
  иконки из репозитория, а не загруженные файлы.
- Отдавать загруженные файлы лучше с отдельного домена — см. `файлы-и-виджеты.md`.

## Что делать, если очистка невозможна

Бывает функция, где разметку надо показать **как есть**: предпросмотр письма
от клиента, сохранённая страница, отчёт из внешней системы.

Тогда содержимое выносят туда, где оно ничего не может испортить:

1. **Отдельный домен** (не поддомен основного — именно другой домен). Код на нём
   не имеет доступа к кукам и данным основного домена.
2. Показ через `<iframe sandbox>` с этого домена — см. `файлы-и-виджеты.md`.
3. Заголовок `Content-Disposition: attachment` для файлов, которые достаточно скачать,
   а не открывать.

Это единственный честный способ. Вариант «покажем как есть на своём домене, но
аккуратно» не существует.

## Короткий чек-лист

| Проверка | Ответ, который устраивает |
|---|---|
| Данные вставляются как текст по умолчанию | да, фреймворк это делает сам |
| Каждое `v-html` / `dangerouslySetInnerHTML` объяснимо и очищается | да, список мест известен |
| Адреса ссылок из базы проверяются по белому списку протоколов | да |
| HTML-шаблоны писем очищаются DOMPurify с белым списком | да |
| Загруженные SVG не вставляются inline | да |
| Очистка есть и на сервере тоже | да |
