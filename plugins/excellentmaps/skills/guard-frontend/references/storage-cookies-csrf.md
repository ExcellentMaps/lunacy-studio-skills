# Хранилище браузера, куки и CSRF

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

Браузер сотрудника — это чужой компьютер, к которому у вас нет доступа. Всё, что вы
туда положили, может прочитать любой код, оказавшийся на странице, и любой человек,
севший за этот компьютер следующим.

---

## Что где хранить

| Что | Где хранить | Почему именно так |
|---|---|---|
| Токен сессии, ключ входа | **Кука** `HttpOnly` + `Secure` + `SameSite=Lax` | Код страницы её не читает. При XSS сессия не утекает |
| Настройки интерфейса: тема, ширина колонок, выбранный фильтр | `localStorage` | Не секрет. Потеря или подмена ничего не стоит |
| Черновик формы, шаг мастера | `sessionStorage` | Живёт до закрытия вкладки — это уместно |
| Данные клиентов: телефоны, адреса, суммы, диагнозы | **Нигде.** Только в памяти на время показа | Иначе остаются в браузере после выхода и после увольнения |
| Ключи сервисов, пароли, коды доступа | **Нигде и никогда** | Во фронтенде не бывает секретов |

Две строки требуют пояснения.

**«Данные клиентов — нигде».** Соблазн понятен: список клиентов кешируется
в `localStorage`, и приложение открывается мгновенно. Плата — база лежит на диске
компьютера в незашифрованном виде, переживает выход из системы, переживает увольнение
и уезжает вместе с ноутбуком. Если кеш всё же нужен ради скорости — он живёт в памяти
и умирает вместе с вкладкой.

**«Ключи — нигде».** Не потому, что `localStorage` плохой, а потому, что ключ всё
равно попал в браузер. Подробнее — `зависимости-и-секреты.md`.

## Почему `HttpOnly` — решающий флаг

Флаг `HttpOnly` означает: эта кука отправляется в запросах автоматически, но
JavaScript её не видит. Ни ваш код, ни чужой.

Сравнение в одной ситуации — на странице выполнился чужой код (XSS):

| Где лежит токен | Что происходит |
|---|---|
| `localStorage` | Одна строка — `localStorage.getItem('token')` — и токен ушёл на чужой сервер. Сессия скопирована целиком, вход по паролю не нужен |
| Кука без `HttpOnly` | То же самое: `document.cookie` читается кодом страницы |
| Кука с `HttpOnly` | Прочитать её нельзя. Чужой код может действовать от имени сотрудника, **пока страница открыта**, но унести доступ с собой не может |

Разница принципиальная: в третьем случае атака заканчивается вместе с вкладкой,
в первых двух — продолжается недели, с чужого компьютера, незаметно.

Именно поэтому «хранить токен в localStorage, зато удобно» — плохой размен.
Удобство даёт несколько сэкономленных строк кода, цена — вся система при одном XSS.

Остальные флаги:

| Флаг | Что делает |
|---|---|
| `Secure` | Кука не уходит по открытому `http://`. Без него её можно перехватить в чужом Wi-Fi |
| `Path=/` | Область действия. Обычно весь сайт |
| `Max-Age` / `Expires` | Срок жизни. Должен быть конечным и разумным |
| `__Host-` в начале имени | Дополнительная строгость: браузер примет такую куку только с `Secure`, `Path=/` и без `Domain` |

Ставится всё это **на сервере**, заголовком ответа. Из кода страницы `HttpOnly`-куку
поставить нельзя — в этом и смысл. Серверная часть — `guard-server` и `guard-auth`.

## `SameSite` простыми словами

`SameSite` отвечает на вопрос: отправлять ли куку, если запрос к вашему сайту
инициирован **с чужого сайта**.

| Значение | Когда кука отправляется | Житейски |
|---|---|---|
| `Strict` | Только если человек уже находится на вашем сайте | Самое строгое. Побочный эффект: переход по ссылке из письма или мессенджера открывает сайт «как будто не вошёл» — приходится обновить страницу |
| `Lax` | При переходе по обычной ссылке — да. При отправке формы или фонового запроса с чужого сайта — нет | Разумное умолчание для CRM. Ссылка из письма работает, а скрытая форма с чужого сайта — нет |
| `None` | Всегда | Требует `Secure`. Нужно, только если ваш сайт работает внутри чужого iframe или фронтенд и API живут на разных доменах |

Практический вывод: **`Lax`** — вариант по умолчанию. `Strict` — если систему
открывают только закладкой и переходы из почты не нужны. `None` ставят, когда без
него ломается работа, и тогда CSRF-защита обязана быть отдельно.

Современные браузеры при отсутствии флага ведут себя примерно как `Lax`, но
полагаться на умолчание не стоит: оно зависит от браузера и его версии. Флаг
выставляется явно.

## Очистка при выходе

В кабинете один компьютер на смену. Человек нажимает «Выйти», встаёт, садится
следующий. Всё, что осталось в браузере, — его.

Что должно происходить по кнопке «Выйти»:

```js
async function выход() {
  await fetch('/api/logout', { method: 'POST', credentials: 'include' })  // 1

  localStorage.clear()                                                    // 2
  sessionStorage.clear()

  if ('caches' in window) {                                               // 3
    for (const имя of await caches.keys()) await caches.delete(имя)
  }
  if (indexedDB.databases) {                                              // 4
    for (const db of await indexedDB.databases()) indexedDB.deleteDatabase(db.name)
  }

  window.location.replace('/login')                                       // 5
}
```

1. 🔴 **Главный шаг — первый.** Сервер обязан погасить саму сессию. Очистка браузера
   без этого — косметика: токен уже мог быть скопирован, и он останется рабочим.
2. Очистка своих ключей. `clear()` вычищает и то, что положили забытые библиотеки.
3. Кеш Service Worker: там лежат ответы API, то есть данные клиентов.
4. IndexedDB — туда кладут офлайн-копии списков.
5. `replace`, а не `href`: страница с данными не остаётся в истории и не открывается
   кнопкой «Назад».

Рядом с этим — автоматический выход по бездействию и короткий срок жизни сессии.
Это уже `guard-auth`.

## CSRF: что это

Бытовая аналогия. У вас есть пропуск в здание, турникет открывается по нему
автоматически. Человек на улице не может отобрать у вас пропуск — но может уговорить
вас пройти через турникет и нажать в лифте нужную ему кнопку. Пропуск ваш, действие
ваше, замысел чужой.

Технически: сотрудник авторизован в CRM, у него в браузере живая кука сессии.
Он открывает в соседней вкладке постороннюю страницу — из письма, из мессенджера,
из поиска. Эта страница молча отправляет запрос на адрес вашей CRM. Браузер
**прикладывает куку автоматически** — он всегда так делает. Сервер видит корректно
авторизованный запрос и выполняет его: удаляет клиента, меняет реквизиты, создаёт
нового администратора.

Сотрудник при этом ничего не видел.

### Когда это актуально, а когда нет

| Как аутентифицируется приложение | CSRF актуален? |
|---|---|
| Кука с сессией, браузер прикладывает её сам | **Да.** Это классический случай |
| Заголовок `Authorization: Bearer ...`, токен подставляет код страницы | **Нет.** Чужая страница не может добавить этот заголовок к запросу — его надо знать и явно подставить |
| Кука + токен в заголовке одновременно | Да, по кукам. Защита нужна |

Отсюда частая путаница: команда читает про CSRF, спорит, ставит защиту там, где она не
нужна, и не ставит там, где нужна. Вопрос ровно один: **чем сервер узнаёт сотрудника**.

### Три способа защиты

| Способ | Как работает | Замечание |
|---|---|---|
| **1. `SameSite=Lax` (или `Strict`)** | Браузер сам не приложит куку к запросу, начатому с чужого сайта | Основная линия. Закрывает большинство случаев и не требует кода |
| **2. CSRF-токен** | Сервер выдаёт случайное значение, страница отправляет его в заголовке или в поле формы, сервер сверяет | Классика. Чужая страница значения не знает. Нужен для форм и для случаев `SameSite=None` |
| **3. Проверка `Origin` / `Referer`** | Сервер отклоняет изменяющие запросы, у которых источник не ваш домен | Простая дополнительная проверка на сервере. Как единственная — слабовата, как дополнение — полезна |

Практический набор для CRM: **1 + 3**, а при формах и сторонних сценариях — плюс 2.

⚠️ Два уточнения, которые часто пропускают:

- Защита нужна на **изменяющих** запросах (`POST`, `PUT`, `PATCH`, `DELETE`).
  Если изменяющее действие сделано через `GET` — оно уязвимо по определению, и это
  чинится не CSRF-токеном, а исправлением метода.
- CSRF-токен не спасает от XSS. Чужой код на вашей же странице спокойно прочитает
  токен и приложит его. Это разные задачи и разные разделы.

## Что проверить

| Проверка | Как |
|---|---|
| У куки сессии стоят `HttpOnly`, `Secure`, `SameSite` | DevTools → Application → Cookies |
| `document.cookie` не показывает сессию | консоль браузера |
| В `localStorage` нет токенов и данных клиентов | DevTools → Application |
| После «Выйти» в браузере ничего не осталось | повторный осмотр Application |
| После «Выйти» старый токен не работает | запрос к API со старым токеном должен получить отказ |
| Изменяющие действия не делаются через `GET` | поиск по коду |

Серверная сторона этих же вопросов — `guard-server` и `guard-auth`.
