## Что такое хеш и чем его считать

Хеш — это необратимый отпечаток. Из пароля получить отпечаток можно, из отпечатка
пароль — нет. При входе система считает отпечаток от введённого пароля и сравнивает
с тем, что лежит в базе; сам пароль системе знать не нужно ни в какой момент.
Практический смысл один: **когда база утечёт — а базы утекают — в руках у
злоумышленника не будет паролей**. Люди повторяют пароли, поэтому список паролей
из CRM — это заодно доступ к почте и личным кабинетам сотрудников.

| Алгоритм | Годится | Почему |
|---|---|---|
| **bcrypt** | Да | Проверен временем, есть везде, настраиваемая медленность |
| **argon2id** | Да, предпочтительно для нового кода | Устойчив и к видеокартам, и к специальному железу |
| **scrypt** | Да | Требует много памяти, что мешает перебору на видеокарте |
| PBKDF2 | Приемлемо, если нет выбора | Работает, но слабее сопротивляется видеокартам |
| `sha256`, `md5`, `sha1` | 🔴 Нет | Считаются слишком быстро — это и есть проблема |

### Почему не md5 и не sha1

Эти алгоритмы создавались, чтобы считаться **быстро** — для контрольных сумм файлов.
Быстро — ровно то, что нужно тому, кто перебирает пароли: обычная игровая видеокарта
проверяет миллиарды вариантов md5 в секунду. Большая часть базы с md5-паролями
вскрывается в первые часы, и не потому, что md5 «сломан», а потому что он быстрый.
Вдобавок для md5 и sha1 давно умеют находить два разных входа с одинаковым
отпечатком — повод не использовать их нигде, где речь о безопасности.

### Зачем соль

Соль — случайная строка, своя для каждого пользователя, которая подмешивается к
паролю перед счётом отпечатка. Без соли одинаковые пароли дают одинаковые
отпечатки. Значит, видно, у кого пароли
совпадают — в том числе что у владельца пароль как у стажёра, — и заранее
посчитанный словарь («радужные таблицы») вскрывает всю таблицу одним проходом.

С солью словарь приходится считать заново для каждого пользователя. У bcrypt,
argon2id и scrypt соль встроена: генерируется сама и хранится внутри строки
отпечатка — отдельно её заводить не надо, и не надо писать свою.

### Зачем медленность

Хороший алгоритм намеренно тратит время: bcrypt с обычной настройкой считает
отпечаток около 100–300 мс. Живому человеку это незаметно — он входит раз в день.
Перебору это умножает время во столько же раз. Настройка называется «стоимость»
(`cost`, `rounds`, `time_cost`); ориентир — 100–300 мс на одну проверку на боевом
сервере, и пересматривать раз в пару лет: железо становится быстрее.

## Как выглядит правильный хеш в базе

В поле пароля должна быть нечитаемая строка, и по её началу видно алгоритм:

```
$2b$12$Kix8f2h1yM0qZ6bWnQeQeOa7Vv...   ← bcrypt, стоимость 12
$argon2id$v=19$m=65536,t=3,p=4$...      ← argon2id
$scrypt$ln=16,r=8,p=1$...               ← scrypt
```

Тревожные признаки:

| Что видно | Что это значит |
|---|---|
| Читаемый текст | 🔴 Пароли хранятся как есть |
| Ровно 32 / 40 / 64 символа из цифр и букв a–f | 🔴 md5 / sha1 / sha256 без замедления |
| Одинаковая строка у двух людей | 🔴 Соли нет |

### Код

```js
// Node — правильно
const bcrypt = require('bcrypt');
const hash = await bcrypt.hash(password, 12);      // при регистрации
const ok   = await bcrypt.compare(password, hash); // при входе

// Node — неправильно
const hash = require('crypto').createHash('md5').update(password).digest('hex');
```

```python
# Python — правильно
from argon2 import PasswordHasher
ph = PasswordHasher()
hash = ph.hash(password)
ph.verify(hash, password)     # бросает исключение, если не подошёл
```

```sql
-- PostgreSQL (pgcrypto) — правильно
insert into users (login, password_hash)
values ('anna', crypt('пароль', gen_salt('bf', 12)));
-- проверка при входе
select password_hash = crypt(p_password, password_hash) from users where id = 1;
```

Последняя строка — ровно то, что делает живой пример в
`db/archive/33_login_throttle.sql`: отпечаток пересчитывается с той же солью,
которая лежит внутри сохранённой строки, и сравнивается с ней.

## Требования к паролю

**Длина важнее набора символов.** Требование «обязательно цифра, заглавная и знак»
даёт предсказуемый результат: `Parol1!` — короткий и стоящий в словарях перебора
одним из первых. Четыре обычных слова подряд длиннее, запоминаются легче и
перебираются несопоставимо дольше.

| Требование | Рекомендация |
|---|---|
| Минимальная длина | 8 символов, лучше 12 |
| Максимальная длина | Не меньше 64 — иначе менеджеры паролей не работают |
| Обязательные наборы символов | Не требовать; подсказывать, а не запрещать |
| Смена раз в 90 дней | Не делать: люди начинают приписывать номер месяца |
| Проверка по спискам утечек | Делать обязательно |

**Проверка по спискам утечек** — сверка нового пароля со списком тех, что уже
засветились в публичных утечках: такие подбираются с первой попытки независимо от
длины. Минимальный вариант — локальный список из нескольких тысяч самых частых
паролей. Если используется внешний сервис, отправлять только первые символы
отпечатка, но не сам пароль.

## Сессии

Сессия — запись о том, что вот этот браузер вошёл вот под этим человеком.

| Параметр | Ориентир | Почему так |
|---|---|---|
| Срок жизни | 30 дней для CRM, меньше — для доступа к деньгам | Забытая вкладка не живёт вечно |
| Продление активностью | Да, обновлять при каждом запросе | Иначе выкидывает посреди рабочего дня |
| Хранение в браузере | Кука с `HttpOnly`, `Secure`, `SameSite=Lax` | Такую куку не читает посторонний скрипт |
| Идентификатор | Случайный, непредсказуемый (UUID) | Не должен угадываться или считаться из номера пользователя |
| Смена после входа | Обязательно новый | Иначе подсунутая заранее сессия становится сессией вошедшего |
| Чистка просроченных | Регулярно, как в живом примере | Таблица не растёт бесконечно |

**Список устройств.** Сотрудник должен видеть, откуда он входил: устройство, адрес,
когда создана сессия, когда последняя активность и какая из них текущая; рядом с
каждой — кнопка «Завершить». Так устроены `sessions_list` и `session_revoke` в
`db/archive/22_sessions_2fa.sql`. **Принудительное завершение** нужно в трёх видах:
одна сессия, все кроме текущей и — для владельца — все сессии любого сотрудника.

⚠️ **Закрытие доступа сотруднику обязано убивать активные сессии НЕМЕДЛЕННО.**
Не «когда токен протухнет», не «при следующем входе». Это самая частая находка в
CRM: владелец нажал «закрыть доступ», вход действительно закрыт, а открытая вкладка
уволенного работает дни, а иногда месяцы. Правильно — два действия сразу: снять
признак активности **и** удалить все его сессии. Плюс проверять этот признак при
каждом запросе, а не только при входе.

```sql
-- правильно: закрытие доступа = флаг + удаление сессий
update users set active = false where id = p_target;
delete from sessions where user_id = p_target;

-- неправильно: вход закрыт, вкладка живёт
update users set active = false where id = p_target;
```

## Смена пароля

1. **Запросить текущий пароль.** Без этого любой, кто на минуту добрался до
   открытой вкладки — коллега, курьер, человек в кофейне, — меняет пароль и
   запирает владельца снаружи его собственной системы.
2. **Новый пароль ввести дважды.** Опечатка в единственном поле = потеря доступа.
3. **Проверить новый по тем же правилам**, что и при регистрации.
4. **Завершить остальные сессии, текущую оставить.** Смысл смены пароля после
   кражи — выгнать того, кто уже внутри; если чужие сессии живут, смена ничего не
   даёт. А выбрасывать самого человека незачем: он только что доказал, что знает
   старый пароль.
5. **Уведомить владельца аккаунта**: «пароль изменён тогда-то с такого-то устройства».

```js
// Node — правильно
if (!await bcrypt.compare(body.current, user.hash)) return deny();
if (body.next !== body.repeat) return deny('Пароли не совпадают');
await saveHash(user.id, await bcrypt.hash(body.next, 12));
await db.query('delete from sessions where user_id = $1 and token <> $2',
               [user.id, currentToken]);

// Node — неправильно: текущий пароль не спрашивают, чужие сессии живут
await saveHash(user.id, await bcrypt.hash(body.next, 12));
```

Отдельно: **сотрудник не должен менять чужой пароль.** Право сбросить пароль другому —
только у владельца, и сброс должен попадать в журнал.

## Восстановление доступа

Правильная схема — одноразовая ссылка с коротким сроком жизни.

1. Человек вводит почту. Ответ **одинаковый** независимо от того, есть такая почта
   или нет: «если адрес зарегистрирован, письмо отправлено».
2. Если адрес есть — генерируется длинный случайный код, в базе сохраняется его
   **отпечаток** (не сам код) и время истечения: 15–30 минут. В письме — ссылка.
3. По переходу человек задаёт новый пароль. Код помечается использованным.
4. Все сессии этого человека завершаются.

| Требование | Почему |
|---|---|
| Срок жизни 15–30 минут, одноразовость | Старое письмо не открывает доступ спустя месяцы |
| Длинный случайный код, в базе — его отпечаток | Не угадывается; утечка базы не даёт готовых ссылок |
| Лимит на отправку писем | Почтовый ящик нельзя завалить |

⚠️ **Никогда не присылать пароль письмом.** Ни старый (его и так неоткуда взять,
если хеширование правильное), ни новый сгенерированный. Письмо остаётся в почте
навсегда, пересылается, попадает в резервные копии почтового сервиса и читается
любым, кто когда-нибудь получит доступ к ящику. Письмо должно содержать ссылку,
по которой человек **сам** задаёт пароль.
