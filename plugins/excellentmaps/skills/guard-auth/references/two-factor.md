## ⚠️ Прочитать до того, как что-то включать

**Двухфакторка включается самой последней мерой — после всего остального из
`SKILL.md`, и только когда коды восстановления сохранены вне системы.**

Это единственная мера защиты, которая может **навсегда** запереть владельца снаружи
его собственной системы. Остальное чинится: забытый пароль сбрасывается через почту,
блокировка проходит через минуту, права возвращает владелец. С включённой 2FA без
кодов восстановления возвращать некому: телефон утонул, приложение переустановили —
и внутрь не попадает никто.

Порядок, который это исключает:

1. Завести **тестовый** аккаунт и включить 2FA на нём. Выйти. Войти заново с кодом.
2. Убедиться, что коды восстановления работают: войти по одному из них.
3. Убедиться, что использованный код второй раз не работает.
4. Убедиться, что владелец может снять 2FA с чужого аккаунта.
5. Только теперь предлагать 2FA владельцу — и **сначала** попросить его сохранить
   коды восстановления вне системы: распечатать, записать в блокнот, положить в
   менеджер паролей. Не в саму CRM и не в заметки на том же телефоне, где стоит
   приложение с кодами.

Пока эти пять шагов не пройдены, 2FA никому не включается. Живому владельцу — в
последнюю очередь.

## Что такое TOTP простыми словами

На телефоне ставится бесплатное приложение (Google Authenticator, Authy, любое
другое). Один раз оно считывает QR-код со страницы настроек и запоминает секрет.
Дальше оно каждые **30 секунд** показывает новый **шестизначный код**.

При входе после логина и пароля система спрашивает этот код. Сервер считает код у
себя — он знает тот же секрет и текущее время — и сравнивает с введённым. Совпало —
значит, человек держит в руках именно тот телефон.

Важные следствия:

- интернет приложению не нужен: код считается из секрета и часов;
- код живёт 30 секунд, перехваченный — быстро бесполезен;
- система не отправляет никаких СМС: платить не за что, перехватывать нечего;
- **время на телефоне должно быть верным**. Сбитые часы — самая частая причина
  «код не подходит»; допуск в одно окно в обе стороны это сглаживает.

Живой пример — `healing._totp_check` в `db/archive/22_sessions_2fa.sql`: секрет
раскладывается в байты, считается код для текущего 30-секундного шага и для соседних
(`for drift in -1..1`), любое совпадение принимается.

## Как это выглядит для сотрудника

| Момент | Что он видит |
|---|---|
| Включение | Страница с QR-кодом и той же строкой секрета текстом (если камера не работает) |
| Проверка | Поле «введите код из приложения» — без успешной проверки 2FA не включается |
| После включения | Список из восьми кодов восстановления, показанный **один раз** |
| Обычный вход | Логин, пароль, затем отдельный экран с полем на 6 цифр |
| Потерянный телефон | Поле того же экрана принимает код восстановления |

Сотруднику стоит объяснить три вещи: коды из приложения меняются сами и их не надо
никуда записывать; коды восстановления надо сохранить вне телефона; при смене
телефона 2FA нужно переподключить заранее, до того как старый телефон стёрли.

## Безопасный порядок включения

Ошибка, которую делают чаще всего, — включить 2FA сразу при выдаче секрета. Человек
видит QR-код, закрывает вкладку, не настроив приложение, — и войти больше не может.

Правильная последовательность из трёх шагов:

1. **Выдать секрет.** Сгенерировать случайный секрет, сохранить его у пользователя,
   показать QR-код и ту же строку текстом. 2FA при этом **ещё выключена**.
2. **Проверить код.** Человек вводит шестизначный код из приложения. Сервер
   проверяет: не совпало — ничего не включается, можно попробовать снова.
3. **Включить.** Только после успешной проверки поставить признак «2FA включена» и
   сразу выдать коды восстановления.

Ровно так устроена пара `totp_start` / `totp_enable` в живом примере: `totp_start`
только записывает секрет и отдаёт `otpauth://`-строку, а `totp_enabled = true`
появляется внутри `totp_enable` — после успешной проверки кода.

```sql
-- правильно: включение только после проверки
if not healing._totp_check(me.totp_secret, coalesce(p_code, '')) then
  return json_build_object('ok', false, 'error', 'Код не подошёл — проверьте время на телефоне');
end if;
update healing.users set totp_enabled = true, recovery_codes = ... where id = me.id;
```

```sql
-- неправильно: включили вместе с выдачей секрета
update healing.users set totp_secret = secret, totp_enabled = true where id = me.id;
```

## Коды восстановления

Это запасной ключ от двери на случай, когда телефона нет.

| Правило | Как и почему |
|---|---|
| Сгенерировать при включении | Раньше нечего восстанавливать, позже человек уже заперт |
| Показать **один раз** | Вернуться и посмотреть их снова нельзя — иначе украденная сессия выдаёт запасные ключи |
| Хранить хешем, как пароли | Утечка базы не должна давать готовые ключи |
| Каждый одноразовый | Использованный вычёркивается немедленно |
| 8–10 штук | Хватает на годы, список остаётся обозримым |
| Показать, сколько осталось | Человек успеет выпустить новые |
| Дать выпустить новые | После использования нескольких — по паролю и текущему коду |

В живом примере коды генерируются восемью штуками, возвращаются пользователю
**открытым текстом ровно один раз** (в ответе `totp_enable`), а в базу кладутся уже
хешами — `crypt(x, gen_salt('bf'))`. При входе перебираются сохранённые хеши, и
совпавший сразу удаляется из массива:

```sql
if rc = crypt(regexp_replace(p_code, '\D', '', 'g'), rc) then
  code_ok := true;
  update healing.users set recovery_codes = array_remove(recovery_codes, rc) where id = u.id;
  exit;
end if;
```

Строка `array_remove` и есть «вычеркнуть»: второй раз этот код не подойдёт.

## Лимит попыток ввода кода

Шестизначный код — это миллион вариантов. Без ограничения попыток программа переберёт
их за минуты, и вся защита исчезнет. Поэтому неверный код должен растить **тот же
счётчик неудач**, что и неверный пароль, с той же блокировкой.

Так сделано в живом примере: ветка «код не подошёл» увеличивает `failed_attempts` и
ставит `locked_until` ровно так же, как ветка неверного пароля.

```js
// Node — правильно
if (!verifyTotp(user.secret, code)) {
  await bumpFailed(user.id);       // общий счётчик, та же блокировка
  return fail('Код не подошёл');
}
```

```js
// Node — неправильно: пароль под лимитом, код — нет
if (!verifyTotp(user.secret, code)) return fail('Код не подошёл');
```

Отдельно: коды восстановления тоже надо считать. Их меньше и они длиннее, но лимит
нужен по той же причине.

## Если телефон потерян

Порядок для сотрудника:

1. Войти по коду восстановления.
2. Сразу отключить 2FA и подключить заново — на новом телефоне выдастся новый секрет.
3. Сохранить новые коды восстановления; старые после переподключения недействительны.
4. Заодно просмотреть список устройств и завершить сессии со старого телефона.

Если кодов восстановления нет — снять 2FA должен **владелец** через управление
сотрудниками. Значит, такая возможность должна существовать заранее:

- владелец может снять 2FA с аккаунта любого сотрудника;
- это действие пишется в журнал: кто снял, с кого, когда;
- после снятия все сессии этого сотрудника завершаются.

А вот для аккаунта **самого владельца** такой кнопки нет — снимать некому. Отсюда и
требование сохранить его коды восстановления вне системы до включения.

## Проверка, что нет обходного пути

2FA, которую можно обойти, хуже отсутствующей: она создаёт ощущение защиты. Проверять
надо не «включается ли», а **можно ли войти мимо неё**.

| Что проверить | Как | Плохой результат |
|---|---|---|
| Старый эндпоинт входа | Найти в коде все точки входа; вызвать прежнюю напрямую | 🔴 Вход прошёл без кода |
| Отсутствующее поле кода | Отправить запрос входа вообще без поля с кодом | 🔴 Пустое значение прошло проверку |
| Пустая строка и `null` | То же с `""`, `null`, пробелом | 🔴 Проверка пропустила |
| Повторное использование кода | Ввести один и тот же код дважды подряд | 🟠 Перехваченный код работает второй раз |
| Код восстановления повторно | Использовать один код дважды | 🔴 Коды не одноразовые |
| Лимит попыток кода | Ввести 20 неверных кодов | 🔴 Блокировки нет |
| Восстановление пароля | Пройти сброс пароля до конца | 🔴 После сброса пускает без кода |

Первый пункт — реальный сценарий, а не теория: новую проверку входа добавили, а
старая функция осталась работать параллельно и кода не спрашивает. В живом примере
защита от этого в том, что проверка 2FA стоит **внутри единственной** функции входа
`healing.login`, а не рядом с ней.

Второй пункт закрывается тем, что пустой код не считается отсутствующим:

```sql
if coalesce(u.totp_enabled, false) then
  if coalesce(p_code, '') = '' then
    return json_build_object('ok', false, 'need_code', true,
      'error', 'Введите код из приложения-аутентификатора');
  end if;
  ...
```

Проверки выполняются на **своём** тестовом аккаунте. Подробные сценарии — у
`guard-audit`, раздел «Проверка входа».
