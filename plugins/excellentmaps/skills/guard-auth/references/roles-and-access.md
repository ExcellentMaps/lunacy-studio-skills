## Главное правило

> **Права проверяются на сервере. В каждом запросе. Без исключений.**

Каждая серверная функция и каждый эндпоинт начинается с двух вопросов: «кто это?» и
«можно ли ему именно это?». Не один раз при входе в приложение, а при **каждом**
обращении — потому что обращения приходят не только из вашего интерфейса.

---

## «Спрятанная кнопка — не защита»

Всё, что происходит в браузере, — подсказка для удобства, а не защита. Спрятанная
кнопка «Удалить», серая вкладка «Финансы», роль в `localStorage`, проверка
`if (user.role === 'owner')` в React — это разметка страницы, которая лежит на
компьютере пользователя и принадлежит пользователю.

Почему это переписывается за десять секунд:

- открыть консоль браузера и выполнить `localStorage.setItem('role', 'owner')`;
- открыть вкладку «Элементы» и снять у кнопки атрибут `disabled`;
- вообще не открывать сайт: отправить запрос напрямую любым инструментом, который
  умеет слать HTTP. Никакой ваш JavaScript при этом не выполняется.

Третий способ — основной. Нападающий не «обходит интерфейс», он его просто не
использует. Поэтому вопрос «видна ли кнопка» к безопасности отношения не имеет.
Единственный вопрос: **что сделает сервер, когда запрос придёт**.

```js
// Node — неправильно: решение принимает браузер
if (user.role === 'owner') await api.delete('/clients/' + id);
```

```js
// Node — правильно: решение принимает сервер
app.delete('/clients/:id', async (req, res) => {
  const me = await authenticate(req);            // кто это
  if (!me) return res.status(401).end();
  if (me.role !== 'owner') return res.status(403).end();  // можно ли ему это
  await deleteClient(req.params.id);
});
```

Прятать кнопки при этом всё равно нужно — но как заботу об удобстве: человек не
тыкается в то, что ему всё равно откажут. Защита живёт отдельно и ниже.

⚠️ Отдельно: роль сервер берёт **из своей базы по идентификатору сессии**, а не из
того, что прислал браузер. Роль в теле запроса, в заголовке или в незашифрованном
токене, который никто не перепроверяет, — это роль, которую пользователь назначает
себе сам.

## Типовые роли CRM

| Роль | Смысл |
|---|---|
| **Владелец** | Отвечает за бизнес. Всё, включая права других и закрытие доступа |
| **Руководитель** | Ведёт отдел: видит работу сотрудников и отчёты, но не управляет доступом |
| **Менеджер** | Работает со своими клиентами и сделками |
| **Маркетолог** | Работает с рекламой и рассылками, к деньгам и карточкам отношения не имеет |
| **Бухгалтер** | Работает с платежами и документами, но не ведёт клиентов |

Матрица «кто что может» — образец, который подгоняется под конкретный бизнес.
Важно, чтобы такая таблица **существовала** и сверялась с кодом.

| Действие | Владелец | Руководитель | Менеджер | Маркетолог | Бухгалтер |
|---|---|---|---|---|---|
| Видеть своих клиентов | да | да | да | нет | нет |
| Видеть всех клиентов | да | да | нет | нет | нет |
| Редактировать карточку клиента | да | да | свои | нет | нет |
| Удалять клиента | да | нет | нет | нет | нет |
| Экспорт базы в файл | да | по решению владельца | нет | нет | нет |
| Видеть суммы и платежи | да | да | по своим сделкам | нет | да |
| Проводить платежи и возвраты | да | нет | нет | нет | да |
| Запускать рассылку по базе | да | нет | нет | с подтверждением | нет |
| Видеть контакты клиентов списком | да | да | свои | нет | нет |
| Заводить сотрудников и менять роли | да | нет | нет | нет | нет |
| Закрывать доступ сотруднику | да | нет | нет | нет | нет |
| Видеть журнал действий | да | свой отдел | нет | нет | нет |
| Менять настройки системы | да | нет | нет | нет | нет |

Два правила, которые видно из таблицы:

- **экспорт и рассылка — отдельные права**, а не «часть просмотра»: это две двери,
  через которые база уходит наружу целиком;
- **управление доступом — только у владельца**. Сотрудник, который может менять
  роли, может сделать владельцем себя.

## IDOR: доступ к чужим записям

**Что это бытовым языком.** Открыли карточку клиента, в адресе видно `/clients/348`.
Поменяли 348 на 349 — открылась чужая карточка, к которой отношения нет. Ключ от
своей квартиры открывает соседнюю, потому что на двери просто написан номер.

**Как это возникает.** Не по злому умыслу и не по невнимательности — из-за того, что
в коде забывают **вторую** проверку:

> «Имеет ли этот сотрудник право смотреть клиентов **вообще**» и «имеет ли он право
> смотреть **именно этого** клиента» — это две **разные** проверки. Первую пишут
> почти всегда. Вторую забывают.

Первая — про роль: менеджеру раздел клиентов доступен. Вторая — про конкретную
запись: этот клиент закреплён за другим менеджером. Код, где есть только первая,
выглядит совершенно правильно и проходит ревью.

```python
# Python — неправильно: проверена только роль
@app.get('/clients/<int:cid>')
def client(cid):
    if not current_user.can('clients.view'): abort(403)
    return db.get_client(cid)          # чей это клиент — не проверено
```

```python
# Python — правильно: запись берётся сразу с условием принадлежности
@app.get('/clients/<int:cid>')
def client(cid):
    if not current_user.can('clients.view'): abort(403)
    row = db.get_client_for(cid, current_user)   # where id=? and owner_id=?
    if row is None: abort(404)
    return row
```

Приём из правого примера — самый надёжный: условие принадлежности встроено в сам
запрос к базе, поэтому «забыть проверку» технически негде. В PostgreSQL то же самое
делается политиками уровня строк (RLS) — см. `guard-data`.

**Как проверить.** На **своём** тестовом аккаунте с урезанной ролью:

1. Завести тестового сотрудника с минимальной ролью.
2. Войти под ним, открыть доступную ему запись, записать её номер.
3. Подставить номер чужой записи.
4. Правильный результат — отказ. Неправильный — данные открылись.

То же самое повторить для заказов, заявок, чатов, файлов, платежей и **действий**:
удаление и редактирование чужой записи проверяются отдельно от просмотра.

Отвечать на чужую запись лучше «не найдено», а не «доступ запрещён»: «запрещено»
подтверждает, что такая запись существует.

## Массовое присвоение полей

**Что происходит.** Форма редактирования профиля присылает имя и телефон. Сервер
берёт всё, что пришло, и записывает в таблицу одной командой. Пользователь
дописывает в запрос лишнее поле:

```json
{ "name": "Анна", "phone": "+7...", "role": "owner", "is_owner": true }
```

Сервер послушно сохраняет и роль тоже. Сотрудник с минимальными правами стал
владельцем, не тронув ни одной кнопки. Так же дописываются `discount`, `balance`,
`user_id`, `confirmed` — всё, что есть в таблице.

```js
// Node — неправильно: в базу уходит всё, что прислали
await db.users.update({ id: me.id }, req.body);
```

```js
// Node — правильно: белый список полей
const ALLOWED = ['name', 'phone', 'avatar'];
const patch = {};
for (const k of ALLOWED) if (k in req.body) patch[k] = req.body[k];
await db.users.update({ id: me.id }, patch);
```

Правило простое: **из запроса берутся только явно перечисленные поля**. Не «все,
кроме запрещённых» — такой список забывают дополнить, когда в таблицу добавляют
новую колонку. Именно белый список, который приходится осознанно расширять.

Поля вроде роли, признака владельца, баланса и статуса оплаты не меняются
пользовательскими формами вообще — только отдельными действиями со своей проверкой
прав и записью в журнал.

## Отзыв доступа

Что должно произойти **немедленно** при увольнении:

| Шаг | Почему немедленно |
|---|---|
| Снять признак активности | Новый вход закрыт |
| Удалить все его сессии | Иначе открытая вкладка работает дни и недели |
| Отозвать личные ключи и токены интеграций | Доступ через API живёт отдельно от входа |
| Снять признак «доверенное устройство», если он есть | Иначе повторный вход пройдёт легче |
| Переназначить его клиентов и сделки | Работа не теряется, и видно, к кому перешла |
| Записать всё в журнал | Кто закрыл доступ, когда, чьи записи переданы |

⚠️ Проверять признак активности нужно **при каждом запросе**, а не только при входе —
иначе первые два шага не связаны между собой и второй легко забыть. В живом примере
`db/archive/33_login_throttle.sql` признак `active` проверяется прямо в функции входа,
до проверки пароля:

```sql
if not coalesce(u.active, true) then
  return json_build_object('ok', false, 'error', 'Доступ закрыт — обратитесь к владельцу');
end if;
```

Проверка занимает минуту: закрыть доступ тестовому сотруднику и обновить его открытую
вкладку. Он должен быть выброшен сразу. Это самая частая находка в CRM — код есть,
а сессия жива.
