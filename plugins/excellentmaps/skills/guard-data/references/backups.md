# Резервные копии и проверенное восстановление

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

---

Самая частая иллюзия защищённости в проектах. Копии «есть» почти у всех,
работающие — у меньшинства, и разница выясняется в единственный момент, когда
это уже нельзя исправить.

---

## 1. Три условия настоящей копии

Копия настоящая только при выполнении всех трёх. Не двух из трёх.

**1. Она делается автоматически.** Не «когда вспомню» и не «перед крупными
изменениями»: человек делает копию регулярно ровно до первой напряжённой недели,
а инцидент случается именно тогда, когда все заняты.

**2. Она лежит не на том же сервере.** См. раздел 6 — нарушают чаще остальных.

**3. Из неё хоть раз восстанавливались.** Непроверенная копия — это файл
неизвестного содержания: он может быть обрезан, собран с ошибкой, содержать
структуру без данных или данные без структуры. Узнать это в момент аварии —
худший из возможных вариантов.

---

## 2. Расписание и сколько хранить

Два параметра надо назвать явно, до настройки: **сколько данных допустимо
потерять** (суточная копия означает потерю суток работы) и **сколько времени
допустимо лежать** — восстановление большой базы это часы, а не минуты.

| Копия | Частота | Сколько хранить |
|---|---|---|
| Ежесуточная | Каждую ночь | Последние 7–14 |
| Еженедельная | Раз в неделю | Последние 4–8 |
| Ежемесячная | Раз в месяц | Последние 6–12 |

Зачем несколько уровней: не все аварии видны сразу. Тихое повреждение данных
может обнаружиться через месяц, когда все суточные копии уже содержат поломку.

Отдельно: **копии тоже имеют срок жизни**. Данные, удалённые из базы по сроку
хранения, живут в копиях, пока те не истекут (`personal-data.md`).

## 3. Готовый скрипт: pg_dump и ротация

Сохранить как `/opt/backup/pg-backup.sh`, дать право на выполнение (`chmod 700`).

```bash
#!/usr/bin/env bash
# Резервная копия PostgreSQL: дамп, ротация, выгрузка наружу.

set -euo pipefail
# -e — оборвать скрипт при первой же ошибке, а не идти дальше молча
# -u — падать при обращении к незаданной переменной (опечатка в имени)
# -o pipefail — ошибка в ЛЮБОМ звене конвейера: иначе неудачный pg_dump
#     в паре с удачным gzip выглядит успехом

DB_URL="postgresql://backup_user@127.0.0.1:5432/postgres"  # роль только на чтение
DEST="/opt/backup/daily"                 # куда складывать локально (временно)
KEEP=14                                  # сколько суточных копий держать
STAMP="$(date +%Y-%m-%d_%H%M)"           # метка времени в имени файла
FILE="$DEST/db_${STAMP}.sql.gz"          # итоговый путь к копии
LOG="/var/log/pg-backup.log"             # журнал самого бэкапа

mkdir -p "$DEST"                         # каталог может не существовать
echo "[$(date -Is)] начало" >> "$LOG"

# --- 1. Сам дамп -------------------------------------------------------
# --format=plain — обычный SQL-текст: читается глазами, разворачивается psql
# --no-owner — не привязывать объекты к владельцу: иначе восстановление
#     в другую базу упрётся в чужие роли
pg_dump "$DB_URL" --format=plain --no-owner | gzip -9 > "$FILE"

# --- 2. Проверка, что файл не пустой -----------------------------------
# Дамп в сотню байт — файл с ошибкой, а не копия базы. Порог подберите под
# свою базу: заведомо ниже нормы, но заведомо выше «пустышки».
MIN_BYTES=10240
SIZE="$(stat -c%s "$FILE")"
if [ "$SIZE" -lt "$MIN_BYTES" ]; then
  echo "[$(date -Is)] ОШИБКА: копия слишком мала ($SIZE байт)" >> "$LOG"
  exit 1                                 # ненулевой код -> cron пришлёт письмо
fi

# --- 3. Проверка, что архив читается -----------------------------------
# gzip -t распаковывает в никуда и проверяет целостность. Ловит обрыв записи.
gzip -t "$FILE"

# --- 4. Шифрование -----------------------------------------------------
# Копия базы клиентов — та же база, только без защиты приложения.
# Открытый ключ на сервере, закрытый — НЕ здесь: сервер может создать
# новую копию, но не прочитать старые.
gpg --batch --yes --encrypt --recipient backup@example.com "$FILE"
rm -f "$FILE"                            # незашифрованный оригинал не оставляем
FILE="${FILE}.gpg"

# --- 5. Выгрузка на другой носитель ------------------------------------
# Главный пункт. Копия рядом с базой не является копией (см. раздел 6).
# Подставьте своё: rclone в объектное хранилище, rsync на другой сервер.
# Учётные данные — в отдельном файле с правами 600, а не в скрипте.
rclone copy "$FILE" remote:crm-backups/daily/ --config /root/.rclone.conf

# --- 6. Ротация --------------------------------------------------------
# Оставляем KEEP самых свежих локально, остальные удаляем.
# ls -1t — по времени, новые сверху; tail -n +N — всё с (N)-й строки.
# В удалённом хранилище ротацию задавайте ЕГО правилами жизненного цикла:
# тогда старые копии нельзя стереть со взломанного сервера.
ls -1t "$DEST"/db_*.sql.gz.gpg 2>/dev/null | tail -n "+$((KEEP+1))" | xargs -r rm -f

echo "[$(date -Is)] готово: $FILE ($SIZE байт)" >> "$LOG"
```

Постановка в расписание (`crontab -e`):

```cron
# Каждую ночь в 03:17, не ровно в 03:00: в круглые часы на сервере
# просыпаются сразу все задачи. Ошибки cron шлёт на MAILTO.
MAILTO=admin@example.com
17 3 * * * /opt/backup/pg-backup.sh >> /var/log/pg-backup.log 2>&1
```

🟠 Отдельно настройте уведомление о том, что копия **не** сделалась: тишина
в почте выглядит одинаково и при успехе, и при сломанном cron. Простейший
вариант — внешний сервис, которому скрипт «отмечается» после успеха и который
пишет вам, если отметки не было дольше суток.

## 4. Проверка восстановления раз в квартал

Восстановление проверяется на **отдельной пустой базе**, а не в бою. Поставьте
это в календарь: без напоминания проверка не делается.

```bash
# 1. Пустая база под проверку — рядом с боевой её быть не должно
createdb -h test-host restore_check

# 2. Расшифровать и восстановить. time — чтобы знать время простоя.
# ON_ERROR_STOP=1 — остановиться на первой ошибке; без него psql проглотит
# сбои и отрапортует об успехе на битом дампе.
time (gpg --decrypt db_2026-09-14.sql.gz.gpg | gunzip | psql -h test-host -d restore_check -v ON_ERROR_STOP=1)

# 3. После проверки базу удалить: это копия персональных данных
dropdb -h test-host restore_check
```

**Чеклист «что проверить после восстановления»:**

| Проверка | Как |
|---|---|
| Прошло без ошибок | В выводе нет `ERROR`, команда вернула 0 |
| Все таблицы и число строк | Сравнить с боевой базой по ключевым таблицам |
| Последняя запись свежая | Максимальная дата в таблицах ≈ время снятия копии |
| Функции и триггеры на месте | Журнал ведётся триггерами — без них копия неполна |
| Права и политики восстановились | Иначе поднятая база окажется открытой наружу |
| Расширения установлены | `pgcrypto` и подобные — без них не заработает вход |
| Приложение поднимается на ней | Самая честная проверка: подключить стенд и войти |
| Сколько времени это заняло | Это и есть ваше реальное время простоя |
| Вложения и файлы | Обычно их **нет** в дампе базы — копируются отдельно |

Последняя строка — частая находка: дамп содержит ссылки на файлы, а сами файлы
лежат в хранилище и в резервную копию базы не попадают. Результат проверки
записать: дата, что проверяли, сколько заняло, что не сошлось.

## 5. Шифрование копий и доступ к ним

Копия базы клиентов — это та же база, только без прав доступа, без защиты
приложения и без журнала обращений: всё, что защищало данные в бою, к файлу
дампа не относится. Отсюда правила:

- копии шифруются **до** отправки в хранилище, ключ расшифровки не лежит
  ни на том же сервере, ни в том же хранилище;
- на сервере достаточно открытого ключа: он позволяет создать копию, но не прочитать старые;
- доступ к хранилищу — у минимального числа людей и отдельно от доступа
  к серверу; скачивание копии — событие для журнала (`audit-log.md`).

🟠 Проверьте отдельно, не лежит ли копия в каталоге, который отдаёт веб-сервер:
дамп, доступный по прямой ссылке, — это утечка базы без всякого взлома.

## 6. ⚠️ Почему копия рядом с базой не спасает

Самая распространённая ошибка: копии складываются в папку на том же сервере,
где работает база. Это защищает ровно от одного случая — «случайно удалили
строки в таблице», и не защищает от всего остального.

| Что происходит | Что случается с локальной копией |
|---|---|
| Шифровальщик зашифровал сервер | Шифрует и папку с копиями — он не различает файлы |
| Отказ диска | Оригинал и копия лежали на одном диске. Нет ни того, ни другого |
| Хостинг удалил аккаунт | За неоплату, по ошибке, по жалобе. Уходит машина целиком |
| Пожар или отключение датацентра | То же самое, только медленнее |
| Взлом сервера | Копии удаляют первым делом, чтобы исключить откат |
| Ошибка в скрипте выкладки | `rm -rf` по неверному пути уносит и копии |

Общее у всех строк: **один инцидент уносит и оригинал, и копию одновременно**.
Именно поэтому условие «не на том же сервере» стоит вторым в разделе 1.

Минимально достаточно: объектное хранилище другого провайдера или второй сервер
в другом датацентре. Хорошо, если у хранилища включена защита от удаления
и своя ротация — тогда копии не стереть даже со взломанного сервера.

## Что сделать по этому справочнику

1. Проверить три условия из раздела 1. Честно, по каждому.
2. Настроить скрипт и cron (раздел 3) с уведомлением о несделанной копии.
3. Проверить, что копия уходит **за пределы** сервера (раздел 6).
4. Зашифровать копии и разобраться с доступом к ним (раздел 5).
5. Провести восстановление на пустой базе по чеклисту (раздел 4), записать
   результат и поставить следующую проверку в календарь — через квартал.
