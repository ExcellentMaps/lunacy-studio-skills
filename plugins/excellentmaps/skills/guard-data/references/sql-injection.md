# SQL-инъекции: как возникают и как закрываются

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

---

SQL-инъекция — это когда текст, который ввёл человек, база понимает как команду,
а не как данные. Уязвимости больше тридцати лет, и она до сих пор в числе первых
причин утечек: её порождает самый естественный способ собрать запрос — склейка.

---

## 1. Откуда она берётся

Запрос собирается склейкой:

```js
// неправильно
const sql = "select * from clients where name = '" + input + "'";
```

Пока в поле пишут «Иванов», всё работает. Но база получает не «запрос и данные»,
а **одну строку текста**, и разбирает её целиком как команду. Кавычка внутри
введённого текста закрывает строку, а всё, что после, становится командой.

Введём в поле поиска `' or '1'='1` — и база увидит:

```sql
select * from clients where name = '' or '1'='1'
```

Условие истинно для каждой строки — вернётся вся клиентская база. Дальше по той
же схеме приделывается `union select` (вытащить чужие таблицы, включая
пользователей и хеши паролей) или `; drop table ...`, если драйвер разрешает
несколько команд в одном запросе.

Ключевая мысль: дело не в «плохих символах». Дело в том, что данные и команда
едут по одному каналу, и база не может их различить.

---

## 2. Почему параметризация решает проблему полностью

Параметризованный (подготовленный) запрос отправляет базе **две вещи отдельно**:
текст команды с метками на месте значений (`where name = $1`) и сами значения —
отдельным списком.

База сначала разбирает команду — без значений, их там ещё нет. Структура
зафиксирована. Только потом значения подставляются в готовые ячейки, уже как
данные. Изменить структуру команды они физически не могут: разбор закончился.

Поэтому текст `' or '1'='1` в параметре — это просто фамилия. Странная фамилия,
которую в базе никто не найдёт. Экранировать ничего не надо, чёрные списки
символов не нужны, «опасные слова» вырезать не нужно.

⚠️ Это не «улучшение защиты», это её полное решение — но только для значений.
Про имена таблиц и колонок см. раздел 5.

## 3. Примеры на разных стеках

**Node.js, драйвер `pg`**

```js
// неправильно
const r = await db.query(
  `select * from clients where phone = '${phone}'`);

// правильно
const r = await db.query(
  'select * from clients where phone = $1', [phone]);
```

**Python, `psycopg`**

```python
# неправильно
cur.execute("select * from clients where phone = '%s'" % phone)
cur.execute(f"select * from clients where phone = '{phone}'")

# правильно — запятая, а не %. Подстановку делает драйвер, не Python
cur.execute("select * from clients where phone = %s", (phone,))
```

Разница между `%` и запятой выглядит опечаткой, а означает разницу между дырой
и защитой. Это самая частая ошибка в Python.

**PHP, PDO**

```php
// неправильно
$st = $pdo->query("select * from clients where phone = '$phone'");

// правильно
$st = $pdo->prepare('select * from clients where phone = ?');
$st->execute([$phone]);
```

Отдельно для PHP: в настройках PDO должно быть
`PDO::ATTR_EMULATE_PREPARES => false` — при эмуляции подстановку делает драйвер
строкой на своей стороне, и часть гарантий теряется.

**Go, `database/sql`**

```go
// неправильно
rows, err := db.Query("select * from clients where phone = '" + phone + "'")

// правильно
rows, err := db.Query("select * from clients where phone = $1", phone)
```

**PostgreSQL, функция внутри базы.** В `plpgsql` обычный запрос параметризуется
сам. Опасен только `execute` со склеенной строкой:

```sql
-- неправильно
execute 'select * from healing.clients where name = ''' || p_name || '''';

-- правильно
execute 'select * from healing.clients where name = $1' using p_name;
```

## 4. ORM не спасает автоматически

Заблуждение: «у нас ORM, инъекций быть не может». Обычные методы вроде
`findMany({ where: { phone } })` действительно безопасны, но остаются три щели.

**Raw-запросы.** Любой ORM даёт аварийный выход в чистый SQL, и им пользуются,
когда запрос сложный. Внутри raw-строки действуют ровно те же правила.

```js
// неправильно — шаблонная строка собирается ДО того, как её увидит ORM
prisma.$queryRawUnsafe(`select * from clients where phone = '${phone}'`);

// правильно — тег превращает подстановки в параметры
prisma.$queryRaw`select * from clients where phone = ${phone}`;
```

**Сортировка из пользовательского ввода.** Клиент присылает «сортировать по
колонке X в порядке Y», и это подставляется в `order by`. Имя колонки
параметром не передаётся (раздел 5) — нужен белый список.

**`LIKE` с подстановкой.** Даже в параметре символы `%` и `_` остаются
служебными для самого оператора `LIKE`. Инъекции команд тут нет, но пользователь
пришлёт `%`, и поиск вернёт всю таблицу — тихая выгрузка базы через форму поиска.
Экранировать эти символы или ограничивать длину и число результатов.

## 5. Имена таблиц и колонок параметрами не закрываются

Параметр — это всегда **значение**. Имя таблицы, имя колонки, направление
сортировки, ключевые слова — часть структуры команды, и параметр на их месте
стоять не может: база просто не примет такой запрос.

Единственный рабочий способ — белый список: сопоставить пришедшее значение
с заранее известным набором и взять свою строку, а не пользовательскую.

```js
// неправильно
db.query(`select * from clients order by ${req.query.sort} ${req.query.dir}`);

// правильно: пользовательский ввод выбирает вариант, но не становится запросом
const COLS = { name: 'name', date: 'created_at', phone: 'phone' };
const col  = COLS[req.query.sort] ?? 'created_at';
const dir  = req.query.dir === 'asc' ? 'ASC' : 'DESC';
db.query(`select * from clients order by ${col} ${dir}`);
```

Обратите внимание: в запрос подставляются строки из **вашего** кода.
Ввод пользователя работает только как ключ поиска по словарю.

Фильтрация вида «вырезать кавычки и точки с запятой» белым списком не является:
способов обойти чёрный список всегда больше, чем записей в нём.

## 6. Коротко про NoSQL

В базах вроде MongoDB запросы — это не строки, а структуры данных, и склейки
текста нет. Но подмена возможна: если тело запроса из браузера кладётся в фильтр
целиком, вместо строки приезжает объект с оператором. Вместо `{ login: "ivan" }`
приходит `{ login: { "$ne": null } }` — «логин не пустой», то есть любой.

Защита та же по смыслу: проверять **тип и форму** пришедших данных перед
использованием (схема валидации), приводить к ожидаемому типу, не передавать тело
запроса в фильтр напрямую. Отдельно: функции, выполняющие JavaScript на стороне
базы (`$where`, `mapReduce`), при пользовательском вводе не применяются.

## 7. Как безопасно проверить своё приложение

⚠️ Проверять надо **чтением кода**, а не подбором строк на живом сайте. Почему:
- успешная проверка означает, что вы уже что-то изменили или выгрузили;
- неуспешная ничего не доказывает — вы просто не угадали форму запроса;
- в журналах остаётся картина атаки, неотличимая от настоящей;
- если сайт не ваш, это отдельный разговор с законом.

Что делать вместо этого:

| Шаг | Как |
|---|---|
| Найти все места сборки SQL | Поиск по коду: `query(`, `execute(`, `$queryRaw`, `raw(`, `EXECUTE ` |
| Найти склейку | Конкатенация и шаблонные строки рядом с SQL: `+ `, `${`, `%s`, `.format(`, `\|\|` |
| Проверить каждое место | Значение едет отдельным параметром — или внутри текста запроса? |
| Проверить `order by` и имена таблиц | Есть белый список — или подставляется ввод? |
| Проверить `LIKE` | Экранируются ли `%` и `_`, есть ли потолок на число результатов |

Если нужна проверка боем — она делается на **тестовой копии** с обезличенными
данными (`personal-data.md`), а не на боевой базе.

Меры, которые уменьшают ущерб, но не заменяют параметризацию: приложение ходит
в базу под ролью с минимальными правами и через ограниченный список функций,
а не напрямую к таблицам (`rls-and-grants.md`); тексты ошибок базы не
показываются пользователю — они подсказывают структуру.
