# Права в базе и защита на уровне строк

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

---

Про то, кто и до чего может дотянуться в базе PostgreSQL. Всё остальное в защите
данных стоит на этом фундаменте: если он перевёрнут, прочие меры маскируют дыру.

---

## 1. Три роли, которые нельзя путать

| Роль | Что это на самом деле | Чем опасна |
|---|---|---|
| `anon` | Публичный ключ. Лежит в коде сайта, его видно в исходном коде страницы. Виден **каждому** человеку в интернете | Всё, что разрешено этой роли, разрешено всем. Без исключений |
| `authenticated` | Вошедший пользователь (если используется встроенная авторизация Supabase) | «Вошёл» не значит «свой». Зарегистрироваться может кто угодно |
| `service_role` | Всемогущий ключ. Обходит защиту на уровне строк и почти все проверки | Утечка = полный доступ к базе. **В браузер не попадает никогда** |

Отдельно есть `public` — это не «неавторизованный», а «вообще все роли сразу»:
права, выданные сюда, автоматически получают и `anon`, и `authenticated`.
Путаница в этом слове — самая частая причина случайно открытой базы.

**Первый вопрос в любом проекте:** что может сделать `anon`? Ответ на него и есть
реальная поверхность атаки, всё остальное — детали. Проверить текущую картину:
`guard-audit`, скрипт `guard-audit/scripts/audit-db.sql`, блок 2.

## 2. Порядок «сначала revoke, потом grant»

Правильная последовательность ровно одна:

1. Забрать всё у всех: `revoke all` со схемы, таблиц, функций, последовательностей.
2. Включить защиту на уровне строк на всех таблицах.
3. Выдать `grant execute` точечно — конкретной функции, конкретной роли.

🔴 **Почему обратный порядок ведёт к катастрофе.**

Типовая история: на старте проекта публичному ключу выдали полный доступ
«чтобы просто заработало», и заодно правило по умолчанию для всех **будущих**
таблиц (`alter default privileges`). Дальше проект рос.

Что из этого следует:

- каждая новая таблица открывается наружу **автоматически**, в момент создания;
- разработчик, который добавляет таблицу, об этом не думает — она «просто работает»;
- 80 миграций спустя команда точечно латает дыры, находя их по одной;
- фундамент при этом остался перевёрнутым, и следующая таблица снова откроется.

Точечное закрытие поверх открытого по умолчанию — это бесконечная работа
с гарантированным отставанием. Закрытое по умолчанию требует усилия один раз.

## 3. USING и WITH CHECK — разные вещи

Защита на уровне строк (RLS) решает не «пустить или нет», а «какие именно строки».
У политики два независимых условия:

| Условие | Что фильтрует | Когда работает |
|---|---|---|
| `USING` | Что **видно** | SELECT, а также какие строки разрешено трогать при UPDATE и DELETE |
| `WITH CHECK` | Что можно **записать** | INSERT и итоговое состояние строки после UPDATE |

🔴 **Политика на запись без `WITH CHECK`.**

Пример на пальцах. Есть таблица заказов, у каждого заказа есть поле «чей».
Политика говорит: «видишь и меняешь свои заказы» — но только через `USING`.

Человек берёт свой заказ (`USING` пропускает — заказ действительно его),
меняет в нём поле «чей» на чужой идентификатор. Проверять итоговое состояние
некому: `WITH CHECK` не написан. Строка уезжает к другому владельцу. Обратный
приём — подставить **себя** владельцем чужой записи и присвоить чужие данные.

```sql
-- неправильно: что видно, ограничено; что записывается — нет
create policy orders_update on healing.orders
  for update to authenticated
  using (owner_id = current_user_id());

-- правильно: ограничено и то, что видно, и то, что получится после записи
create policy orders_update on healing.orders
  for update to authenticated
  using      (owner_id = current_user_id())
  with check (owner_id = current_user_id());
```

🟠 **Политика без указания роли.** Если не написать `TO authenticated`,
политика применяется ко всем ролям, включая `anon`. Частая ошибка: скопировали
политику чтения, переделали под запись, роль указать забыли.

Найти такие: `audit-db.sql`, блоки 5 и 6.

## 4. SECURITY DEFINER и обязательный search_path

`SECURITY DEFINER` означает: функция выполняется с правами того, кто её создал
(обычно — владельца базы), а не того, кто её вызвал. Это нужный механизм:
именно так строится единственная законная дверь в закрытые таблицы.

Но у него есть условие, без которого он превращается в дыру.

**Механика подмены схемы, простыми словами.**

Когда в функции написано `select * from clients`, база должна понять, какая
именно таблица имеется в виду. Она идёт по списку схем — `search_path` —
и берёт первую подходящую. Список этот задаёт **вызывающий**, а не функция.

Значит, атакующий может:

1. Создать свою схему, в которой лежит своя таблица `clients`
   (или своя функция `crypt`, `now`, что угодно).
2. Поставить свою схему первой в `search_path`.
3. Вызвать вашу функцию.

Функция послушно находит **чужую** таблицу вместо настоящей — и выполняет
чужой код с правами владельца базы. Это классический способ повышения привилегий:
обычный пользователь получает полномочия администратора.

Лечится одной строкой — закрепить список схем прямо в функции:

```sql
create or replace function healing.client_save(...)
returns json
language plpgsql security definer
set search_path = healing, pg_temp   -- правильно: список закреплён
as $$ ... $$;
```

`pg_temp` ставится **последним** намеренно: временные объекты не должны
перехватывать имена. Где закрепления нет — `audit-db.sql`, блок 3.

## 5. Вьюхи как тихий обход RLS

Вьюха (сохранённый запрос) по умолчанию выполняется с правами того, кто её создал,
а не того, кто её читает. Владелец таблицы обычно освобождён от политик на своей же
таблице — и вьюха унаследует это освобождение.

Итог: таблица закрыта политиками, а вьюха поверх неё спокойно отдаёт строки,
которые политика запретила. Защита формально включена и при этом не работает.

```sql
-- правильно, PostgreSQL 15 и новее:
alter view healing.clients_public set (security_invoker = true);
```

После этого вьюха выполняется с правами читающего, и политики применяются.
На версиях ниже 15 такой возможности нет — там вьюху над закрытой таблицей
либо не делают, либо закрывают правами полностью. Проверить: блок 7.

## 6. Точечная выдача прав

Как выглядит закрытая схема в рабочем проекте:

```sql
revoke all on schema healing from public;
grant usage on schema healing to anon, authenticated;

revoke all on all tables    in schema healing from anon, authenticated;
revoke all on all functions in schema healing from public, anon, authenticated;

grant execute on function healing.login(text, text)          to anon;
grant execute on function healing.clients_list(int, uuid, text, text) to anon;
-- служебные функции проверки доступа наружу не выдаются намеренно
```

Три правила для этого списка:

- `usage on schema` — это только право «видеть, что схема существует».
  Без него не работает ничего, доступа к данным оно само по себе не даёт.
- В `grant execute` указывается **полная подпись** функции с типами аргументов.
  Если у функции есть перегрузки, права выдаются каждой отдельно.
- Каждая открытая функция обязана **сама** проверять, кто её вызвал.
  Открыв функцию `anon`, вы открыли её всему интернету.

## 7. Автопроверка при каждом обновлении

🟠 **Однократная зачистка прав живёт ровно до следующей миграции.**

Причина не в небрежности. Новая таблица создаётся без включённой защиты строк,
новая функция — доступной для выполнения всем: это поведение базы по умолчанию.
Разработчик, добавляющий функцию, думает о задаче, а не о правах, и проверить
забытое глазами в потоке миграций невозможно.

Значит, нужен не разовый акт, а постоянная проверка. Минимальный набор
контрольных вопросов при каждом обновлении базы:

| Проверка | Что должно получиться |
|---|---|
| Таблицы без включённого RLS | Пусто |
| Права `anon` и `public` на таблицы и вьюхи | Пусто |
| Функции `SECURITY DEFINER` без `search_path` | Пусто |
| Функции, доступные `anon` | Совпадает со списком в коде, строка в строку |
| Политики на запись без `WITH CHECK` | Пусто |

Проверка должна **падать** и останавливать выкладку, а не писать
предупреждение в лог, который никто не читает. Запросы для неё уже готовы —
`guard-audit`, `guard-audit/scripts/audit-db.sql`; их достаточно обернуть в скрипт,
возвращающий ненулевой код при непустом результате.

## Что сделать по этому справочнику

1. Снять картину: `guard-audit`, `guard-audit/scripts/audit-db.sql`. Ничего не меняет.
2. Сделать дамп базы.
3. Прогнать `examples/lock-down-grants.sql` **на копии**, сверив список
   `grant execute` со своим кодом.
4. Проверить, что приложение работает: неверно снятые права ломают его мгновенно.
5. Поставить проверку из раздела 7 в процесс обновления базы.
