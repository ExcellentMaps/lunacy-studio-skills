# Журнал действий

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

---

Журнал отвечает на вопрос «кто это сделал» в тот день, когда что-то пропало.
Он не предотвращает инцидент — он делает его разбираемым. В CRM это не
«хорошо бы», а необходимость: угроза здесь чаще внутренняя, и без журнала
разговор с сотрудником превращается в «я не я».

Вторая, менее очевидная польза: журнал позволяет **доказать, что утечки не было**.
Без него нельзя ни обвинить, ни оправдаться.

---

## 1. Что писать

Не всё подряд. Журнал всего — это шум, в котором ничего не найти, и вдобавок
вторая база персональных данных (раздел 6).

Обязательный минимум:

| Событие | Почему важно |
|---|---|
| Вход в систему | Успешный и неуспешный. Серия неудач подряд — признак подбора |
| Выход и завершение сессии | Восстанавливает картину «кто был в системе в момент X» |
| Изменение прав и ролей | Повышение себе или коллеге — самое опасное действие в системе |
| Смена **чужого** пароля | Способ тихо захватить чужой доступ |
| Создание и закрытие учётной записи | Учётка уволенного, которая ожила, — классика |
| Удаление любых данных | Первое, что спрашивают при разборе |
| Экспорт и массовая выгрузка | С обязательным **числом записей** — см. раздел 3 |
| Отправка сообщений клиентам | Рассылка от имени владельца, отозвать нельзя |
| Изменение настроек безопасности | Отключение проверок, смена ключей интеграций |
| Доступ к особо чувствительным полям | Если такие есть: просмотр диагнозов, вложений |

Не нужно писать: каждый просмотр списка, каждое открытие страницы, каждое
движение по интерфейсу. Это забивает журнал и никого не спасает.

## 2. Состав записи и «было → стало»

Каждая запись должна отвечать на пять вопросов: кто, что, с чем, когда, откуда.

| Поле | Содержимое |
|---|---|
| Кто | Идентификатор сотрудника (не имя — имя меняется) |
| Что | Тип действия из фиксированного списка |
| С чем | Таблица и идентификатор записи |
| Когда | Время с часовым поясом |
| Откуда | IP-адрес, признак устройства или сессии |
| Было → стало | Значения до и после изменения |

Последняя строка — та, ради которой журнал вообще работает. Запись
«менеджер изменил клиента №4711» бесполезна: неизвестно, исправил опечатку
в имени или переписал сумму долга. Запись «поле `role`: `manager` → `owner`»
отвечает на вопрос сразу.

Хранить «было → стало» удобно двумя полями с содержимым строки до и после,
но записывать надо **только изменившиеся поля**, а не всю строку целиком.
Иначе журнал за год станет больше самой базы, и в него попадёт всё
чувствительное, что в строке было.

## 3. Экспорт: число записей обязательно

Для выгрузок одного факта «была выгрузка» мало. Нужно число выгруженных записей
и, по возможности, условия отбора.

Разница между «выгрузил 12 строк по одному клиенту» и «выгрузил 12 000 строк
без фильтра» — это разница между работой и утечкой базы. Без числа записей
эти два события в журнале выглядят одинаково.

То же для рассылок: сколько получателей. Подробнее про экспорт —
`personal-data.md`, раздел 7, и `guard-audit`, блок 9.

## 4. Почему журнал должен вестись на уровне базы

Самая частая ошибка: журнал пишется в коде приложения — там, где обрабатывается
нажатие кнопки. Выглядит логично и работает ровно до первого обхода приложения.

Пути, которые мимо приложения проходят всегда:

- прямой запрос в базу через `psql` или графический клиент;
- админ-панель базы (например, SQL-редактор в панели хостинга);
- фоновая задача, миграция, скрипт разовой правки данных;
- сервисный ключ, обходящий проверки приложения;
- другое приложение или интеграция, работающая с той же базой.

Во всех этих случаях кнопка не нажималась, код приложения не выполнялся,
записи в журнале нет. При этом данные изменились.

**Правильно:** журнал ведётся триггерами на уровне базы. Триггер срабатывает
на изменение строки независимо от того, кто и откуда это изменение сделал.
Обойти его, не имея прав администратора базы, нельзя.

```sql
-- правильно: журнал пишет сама база, на любое изменение таблицы
create trigger clients_audit
  after insert or update or delete on healing.clients
  for each row execute function healing.write_audit();
```

Что при этом остаётся за приложением: события, которых на уровне строк не видно —
вход в систему, неудачная попытка входа, факт экспорта. Их база сама не заметит,
их пишет код. Поэтому в реальности журнал ведётся с обеих сторон, но основа —
триггеры.

## 5. Сотрудник не должен уметь чистить журнал за собой

Журнал, который можно отредактировать, не доказывает ничего. И первое, что
делает человек, заметающий следы, — удаляет свои строки.

Обеспечивается это правами, а не дисциплиной:

| Мера | Как |
|---|---|
| Запись — только через функцию | Роли приложения запрещены `insert`, `update`, `delete` на таблице журнала напрямую |
| Изменение и удаление запрещены всем | `revoke update, delete on healing.audit_log from ...` — для всех ролей приложения |
| Запись только добавлением | Новая строка можно, изменить старую — нельзя |
| Чтение — ограниченной роли | Журнал сам содержит чувствительные сведения |
| Очистка по сроку — только фоновой задачей | Отдельная роль, работающая по дате, а не по выбору строк |
| Копия журнала вне системы | Периодическая выгрузка в место, куда сотрудники не имеют доступа |

Последний пункт закрывает главную дыру: администратор базы технически может
всё, включая удаление журнала. Полностью защититься от него внутри той же базы
нельзя — можно только вынести копию наружу, где его прав нет.

## 6. ⚠️ Журнал не должен стать второй базой персональных данных

Ловушка выглядит так: чтобы журнал был информативным, в него пишут содержимое
изменённых полей. Через год журнал содержит полную историю всех персональных
данных, включая удалённые — и при этом он пережил и удаление карточек, и срок
хранения, и обезличивание тестовой копии.

Чего в журнале быть не должно:

- паролей и их хешей — ни старых, ни новых, ни в поле «было»;
- кодов подтверждения, одноразовых кодов, токенов сессий;
- ключей интеграций и секретов;
- содержимого вложений и свободных полей с диагнозами;
- полных номеров карт и документов.

Как хранить безопасно:

- для чувствительных полей писать факт изменения, а не значения:
  `поле password_hash изменено` вместо старого и нового значения;
- телефоны и почту маскировать, если они нужны для узнавания;
- ссылаться на идентификаторы записей, а не копировать их содержимое.

Срок хранения у журнала свой и, как правило, дольше, чем у данных — иначе
разбор давнего инцидента невозможен. Но он конечен, и старые записи удаляются
фоновой задачей (`personal-data.md`, раздел 3). Конкретные сроки зависят
от юрисдикции — это вопрос к юристу, см. `compliance-testing`.

## 7. Что показывать владельцу

Журнал, который нельзя прочитать, равносилен отсутствующему. Владельцу нужен
не поток строк, а ответы на вопросы. Практически полезны:

| Фильтр | Зачем нужен |
|---|---|
| По сотруднику | «Что делал уволенный за последний месяц» — первый запрос после увольнения |
| По периоду | Привязка к дате инцидента |
| По типу действия | Отдельно: удаления, экспорты, смены прав |
| По записи | «Вся история этого клиента» — кто и когда его менял |
| Только опасные действия | Один переключатель: удаления, экспорт, права, пароли |

Плюс два готовых экрана, которые закрывают большинство реальных случаев:

- **Сводка за неделю:** сколько входов, сколько удалений, сколько выгрузок
  и на сколько записей. Аномалия видна без поиска.
- **Заметное уведомление** при событиях красного уровня: массовая выгрузка,
  повышение прав, смена чужого пароля, серия неудачных входов.

🟠 Уведомление, которое приходит на почту и там теряется, не работает.
Оно должно быть видно в самой системе, при следующем входе владельца.

## Что сделать по этому справочнику

1. Составить список событий из раздела 1 и сверить с тем, что пишется сейчас.
2. Перенести журнал на триггеры уровня базы (раздел 4).
3. Добавить «было → стало» по изменившимся полям.
4. Для экспорта — писать число записей (раздел 3).
5. Закрыть правами изменение и удаление журнала (раздел 5).
6. Вычистить из журнала пароли, коды и чувствительное содержимое (раздел 6).
7. Сделать владельцу экран со сводкой и фильтрами (раздел 7).
