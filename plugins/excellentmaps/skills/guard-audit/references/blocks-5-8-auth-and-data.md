# Блоки 5–8. Вход, база, права и обработка данных

Guard Security Suite © ExcellentMaps — github.com/ExcellentMaps

Четыре блока, которые нельзя проверить снаружи одной командой. Здесь нужен тестовый
аккаунт, доступ к базе и чтение кода.

⚠️ Все проверки делаются на **специально созданном тестовом аккаунте** или на
несуществующем логине. Подбирать пароли к живым учётным записям нельзя — это создаёт
блокировки реальным сотрудникам и мусор в журнале.

---

## Блок 5. Вход

### 5.1 Защита от подбора пароля

Завести тестового сотрудника, затем:

1. Ввести неверный пароль 5–6 раз подряд.
2. Ввести **верный** пароль.

| Результат | Оценка |
|---|---|
| Верный пароль принят сразу | 🔴 Лимита нет. Простой пароль подбирают за минуты |
| Отказ с сообщением о блокировке | ✅ Лимит работает |
| Отказ, но после перезагрузки страницы вход прошёл | 🔴 Счётчик живёт в браузере, не на сервере |

Третий случай встречается чаще всего: счётчик реализован в JavaScript и обходится
клавишей F5.

### 5.2 Перебор логинов

Отдельная проверка, которую почти всегда забывают. Ввести десяток **несуществующих**
логинов подряд.

Если система отвечает быстро и бесконечно — список сотрудников собирается за час,
и дальше подбор идёт точечно, только по существующим аккаунтам.

Должен быть второй, общий счётчик промахов по неизвестным именам.

### 5.3 Текст ошибки

Сравнить дословно два ответа: неверный пароль у существующего логина и вход под
несуществующим логином.

Разный текст («такого пользователя нет» / «неверный пароль») — это подсказка,
которая превращает перебор в точную работу. Правильно: **один и тот же текст**.

То же касается **времени ответа**: если несуществующий логин отвечает мгновенно,
а существующий — через 300 мс (проверка хеша), разницу видно даже без текста.

### 5.4 Сессии

| Проверка | Как проверить | Плохо |
|---|---|---|
| Срок жизни сессии | Оставить вкладку на сутки | Сессия бессрочная |
| Видно ли список устройств | Настройки → безопасность | Списка нет |
| Можно ли завершить чужую сессию | Нажать «Завершить» | Кнопки нет |
| Смена пароля выкидывает другие устройства | Сменить пароль, проверить вторую вкладку | Остальные продолжают работать |
| **Закрытие доступа убивает активные сессии** | Закрыть доступ тестовому сотруднику, обновить его вкладку | 🔴 Продолжает работать |

Последняя строка — самая частая находка в CRM. Уволенный сотрудник не может войти
заново, но его открытая вкладка живёт до истечения токена: дни, а иногда месяцы.

### 5.5 Двухфакторка

Не «включена ли», а **можно ли её обойти**. Проверить:

- нет ли второго, старого эндпоинта входа, который работает без кода;
- что происходит, если в запросе просто не прислать поле с кодом;
- ограничено ли число попыток ввода кода (6 цифр подбираются за минуты без лимита);
- одноразовы ли коды восстановления.

Первый пункт — реальный сценарий: новая проверка входа добавлена, а старая осталась
работать параллельно и кода не спрашивает.

**Чинить:** `guard-auth`.

## Блок 6. Права в базе

Запустить `scripts/audit-db.sql`. Ниже — как читать каждый из восьми его блоков.

| Блок скрипта | Что показывает | Что значит результат |
|---|---|---|
| 1. Таблицы без RLS | Таблицы без защиты на уровне строк | Опасно только в связке с блоком 2. Сами по себе — 🟠 |
| 2. Доступ публичного ключа | **Реальная поверхность атаки** | `DELETE`/`UPDATE` у `anon` — 🔴. `SELECT` у `anon` на таблице с клиентами — 🔴 |
| 3. DEFINER без search_path | Функции с правами владельца базы | 🔴 Классический способ захвата базы |
| 4. Функции, доступные анониму | Единственная законная дверь | Любая лишняя строка — 🔴. Сверять со своим кодом |
| 5. Политики без WITH CHECK | Запись без проверки | 🟠 Можно переписать чужой идентификатор владельца |
| 6. Политики без указания роли | Действуют и на анонима | 🟠 |
| 7. Вьюхи от имени автора | Обход RLS через вьюху | 🟠 |
| 8. Расширения в public | Смешение служебного и своего | 🟡 |

**Главное, что надо понять про блок 2.** Публичный ключ (`anon`) лежит в коде сайта
и виден каждому, кто открыл страницу. Всё, что разрешено ему, разрешено любому
человеку в интернете — без всякого взлома, обычным запросом.

Правильная картина: блок 2 пустой, а вся работа идёт через ограниченный список
функций из блока 4, каждая из которых сама проверяет права вызывающего.

**Чинить:** `guard-data`.

## Блок 7. Права в приложении

### 7.1 Спрятанная кнопка — не защита

Для каждой роли выписать, чего она **не должна** уметь, и попробовать сделать это
запросом напрямую, минуя интерфейс.

Типовые находки:
- кнопки «Удалить» нет, но запрос на удаление проходит;
- раздела «Финансы» в меню нет, но эндпоинт отчёта отвечает;
- сотрудник может сменить чужой пароль или повысить себе роль.

### 7.2 Доступ к чужим записям (IDOR)

На тестовом аккаунте с минимальной ролью подставить в адрес идентификатор чужой
записи: карточки клиента, заказа, чата, файла, платежа.

Правильный результат — отказ. Данные открылись — 🔴.

Частая причина: проверка «имеет ли право смотреть клиентов вообще» есть, а проверки
«имеет ли право смотреть **именно этого** клиента» нет.

### 7.3 Массовое присвоение полей

Отправить в запросе на сохранение профиля лишнее поле: `role`, `is_owner`,
`balance`, `user_id`. Если сервер принимает всё, что прислали, и пишет в базу —
пользователь назначает себя владельцем сам.

Правильно: сервер берёт из запроса только явно разрешённый список полей.

**Чинить:** `guard-auth`.

## Блок 8. Ввод и вывод

### 8.1 SQL-инъекции

Проверяется чтением кода, а не подбором строк на живом сайте. Искать места, где
SQL собирается склейкой с пользовательскими данными: `"SELECT ... " + параметр`.

Особое внимание: сортировка и фильтры (`ORDER BY` из выпадающего списка), поиск
с `LIKE`, динамические имена таблиц и колонок. ORM здесь не спасает автоматически.

### 8.2 XSS

Вписать в текстовое поле безобидную разметку (например, `<b>тест</b>`), сохранить,
открыть запись.

| Результат | Оценка |
|---|---|
| На экране видно `<b>тест</b>` как текст | ✅ Правильно |
| На экране жирное слово «тест» | 🔴 Разметка выполняется |

Проверить поля, которые чаще всего форматируют «для красоты»: комментарии,
описания, шаблоны сообщений, подписи.

### 8.3 Загрузка файлов

- Можно ли загрузить файл не того типа (проверка по расширению вместо содержимого).
- Открывается ли загруженный файл по прямой ссылке без входа.
- Виден ли список файлов, если открыть адрес папки.
- Выполняется ли загруженный HTML или SVG на домене сайта — 🔴, если да.
- Обрабатывается ли `../` в имени файла.

### 8.4 SSRF в интеграциях

Если приложение ходит по адресу, который задаёт пользователь (аватар по ссылке,
вебхук, импорт по URL) — проверить, ограничен ли список адресов.

Без ограничения сервер можно заставить обратиться во внутреннюю сеть или к служебным
адресам облака, недоступным снаружи.

**Чинить:** `guard-data` (SQL), `guard-frontend` (XSS, файлы), `guard-server` (SSRF).

## Итог блоков 5–8

🔴 Красный уровень:

| Находка | Почему |
|---|---|
| Нет лимита попыток входа | Пароль подбирают за минуты |
| Закрытие доступа не убивает сессии | Уволенный продолжает работать |
| Двухфакторку можно обойти старым эндпоинтом | 2FA превращается в декорацию |
| `anon` может писать или удалять в базе | Базу стирают одним запросом |
| `SECURITY DEFINER` без `search_path` | Захват базы |
| Чужая карточка открывается подстановкой номера | Вся клиентская база по одному |
| SQL собирается склейкой строк | Выгрузка или удаление через форму |
| Загруженный HTML выполняется на домене сайта | Кража сессий сотрудников |
