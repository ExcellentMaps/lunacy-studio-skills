## Блок 10. Боты, ИИ и политика доступа

### 10.1 Файлы политики отдаются

Проверить, что все пять действительно доступны по своим адресам — не «лежат в
репозитории», а отдаются сервером:

```bash
for f in robots.txt llms.txt .well-known/ai.txt .well-known/security.txt .well-known/tdmrep.json; do
  printf '%-34s %s\n' "$f" "$(curl -s -o /dev/null -w '%{http_code}' https://ВАШ_ДОМЕН/$f)"
done
```

Ожидается `200` на каждой строке. `404` — файла нет. `403` — его заблокировала
ваша же защита от ботов, что бессмысленно: политику должны читать именно боты.

Отдельно: `security.txt` с **истёкшей датой `Expires` считается недействительным**.
Проверять не только наличие, но и дату внутри.

### 10.2 Заголовок X-Robots-Tag

```bash
curl -sSI https://ВАШ_ДОМЕН/ | grep -i x-robots-tag
```

Мета-теги действуют только на HTML-страницы. Картинки, PDF и выгрузки закрывает
только заголовок. Если его нет — политика дырявая ровно в том месте, где лежат
документы клиентов.

### 10.3 Реакция на ботов

```bash
for ua in "GPTBot/1.0" "ClaudeBot/1.0" "PerplexityBot/1.0" "sqlmap/1.7" "python-requests/2.31"; do
  printf '%-22s %s\n' "$ua" "$(curl -s -o /dev/null -w '%{http_code}' -A "$ua" https://ВАШ_ДОМЕН/)"
done
```

Для закрытой системы ожидается `403`. Для публичного сайта поисковики должны
проходить, а сканеры — нет.

### 10.4 ⚠️ Обратная проверка: не задели ли своих

Это половина блока 10, и её пропускают чаще всего. Блокировка ботов ломает
интеграции тихо — связь обнаруживают через недели.

| Проверка | Команда | Ожидается |
|---|---|---|
| Живой браузер проходит | `curl -A "Mozilla/5.0 (Windows NT 10.0)" -o /dev/null -w '%{http_code}' https://ДОМЕН/` | `200` |
| Продление сертификата не сломано | `curl -o /dev/null -w '%{http_code}' https://ДОМЕН/.well-known/acme-challenge/test` | не `403` |
| Вебхуки проходят | Отправить тестовый запрос на свой адрес вебхука | не `403` |
| Мониторинг проходит | Посмотреть в панели мониторинга, нет ли ошибок с момента включения | без ошибок |

Если живой браузер получает не `200` — это 🔴 **срочно**: защита бьёт по реальным
пользователям, а не по ботам.

**Чинить:** `guard-ai-policy`.

## Блок 11. Журнал действий и резервные копии

### 11.1 Журнал

| Проверка | Плохой ответ |
|---|---|
| Журнал ведётся на уровне базы, а не приложения | Только в приложении — прямой запрос в обход не попадёт в журнал |
| Фиксируются вход, смена прав, смена чужого пароля | Фиксируются только удаления |
| Фиксируется **экспорт** клиентской базы | Не фиксируется — 🔴 для CRM |
| Видно «было → стало» | Только «изменил клиента» |
| Сотрудник не может почистить журнал за собой | Может — журнал бессмысленен |
| Есть срок хранения | Хранится вечно — журнал сам стал базой ПДн |
| В журнал не попадают пароли и коды | Попадают — 🔴 |

Проверка простая: сделать тестовое действие под тестовым сотрудником и убедиться,
что оно в журнале видно, с автором и временем.

### 11.2 Резервные копии

Три условия. Копия считается настоящей, только если выполнены **все три**:

| Условие | Как проверить | Если нет |
|---|---|---|
| Делается автоматически | `crontab -l`, systemd timer, панель хостинга | «Когда вспомню» = не делается |
| Лежит **не на том же сервере** | Посмотреть путь хранения | Пожар, шифровальщик, удаление аккаунта унесут и копию |
| Из неё хоть раз восстанавливались | Спросить владельца прямо | Файл неизвестного содержания |

Третий пункт — ключевой. Непроверенная копия не защищает ни от чего: узнать, что
она битая или неполная, вы сможете только в тот день, когда она понадобится.

Дополнительно проверить: сколько копий хранится, зашифрованы ли они, кто имеет
к ним доступ (копия базы клиентов — это та же база, только без защиты приложения).

**Чинить:** `guard-data`.

## Блок 12. Что владелец должен включить сам

Часть защиты живёт не в коде, а в панелях сервисов. Разработчик её не включит —
нужен человек с доступом к аккаунту.

### ⚠️ Обязательное правило перед тем, как диктовать шаги

**Интерфейсы панелей меняются каждые несколько месяцев.** Названия пунктов меню,
расположение переключателей и даже названия функций перестают совпадать с тем,
что было полгода назад.

Поэтому: **перед тем как рассказать человеку, куда нажимать, откройте актуальную
официальную документацию сервиса и сверьтесь с ней.** Никогда не диктуйте шаги
по памяти — человек не найдёт названный пункт, решит, что ошибся сам, и бросит.

Официальные источники:

| Сервис | Документация |
|---|---|
| Cloudflare | https://developers.cloudflare.com/ |
| Supabase | https://supabase.com/docs |
| GitHub | https://docs.github.com/ |
| Let's Encrypt / certbot | https://eff-certbot.readthedocs.io/ |
| nginx | https://nginx.org/ru/docs/ |
| Docker | https://docs.docker.com/ |

Сверять по документации, а не по статьям в блогах: статьи устаревают и не
обновляются.

### Чеклист действий владельца

**Cloudflare** (если домен подключён):
- блокировка ИИ-краулеров;
- защита от ботов;
- правила WAF;
- ограничение частоты запросов;
- режим «только HTTPS».

**Панель хостинга / облака:**
- снапшоты сервера по расписанию — ⚠️ сделать снапшот **до** работ по безопасности;
- облачный firewall как второй рубеж поверх ufw;
- уведомления о входе в аккаунт хостинга;
- двухфакторка на самом аккаунте хостинга (иначе весь сервер защищён одним паролем).

**GitHub / GitLab:**
- двухфакторка на аккаунте;
- поиск секретов в репозитории;
- защита основной ветки;
- проверка, что репозиторий приватный, если он должен быть приватным.

**Supabase / облачная база:**
- встроенный советник по безопасности (штатный линтер прав и политик);
- проверка, что сервисный ключ нигде не используется на стороне браузера.

**Почта домена:**
- SPF, DKIM, DMARC — иначе от вашего имени рассылают письма клиентам.

**Организационное:**
- у кого есть доступ к серверу, к базе, к почте, к домену — список должен быть
  актуальным;
- что происходит с доступами при увольнении;
- кому звонить, если система недоступна ночью.

Последний пункт не технический, но в момент инцидента он оказывается важнее всех
остальных.

## Итог блоков 10–12

🔴 Красный уровень:

- живой браузер получает не `200` — защита бьёт по своим;
- экспорт клиентской базы не пишется в журнал;
- резервных копий нет, они лежат на том же сервере или из них ни разу не восстанавливались;
- нет двухфакторки на аккаунте хостинга или домена — один пароль открывает всё.
