## Блок 1. Секреты и ключи

**Что ищем:** пароли, ключи, токены, сертификаты — в коде, в конфигах, в истории git,
в собранном фронтенде.

### Почему это первый блок

Утечка ключа обнуляет все остальные слои. Можно идеально настроить firewall, RLS и
двухфакторку — и всё это не имеет значения, если сервисный ключ базы лежит в
публичном репозитории.

### Что проверить

| Где | Что искать |
|---|---|
| Код проекта | `password =`, `api_key =`, `secret =` с реальным значением |
| История git | `.env`, `*.pem`, `*.key`, `secrets.*`, дампы базы среди отслеживаемых файлов |
| Собранный фронтенд (`dist/`, `build/`) | ключи, попавшие в сборку через переменные окружения |
| Конфиги сервера | пароли в открытом виде, права на файлы |
| Скрипты установки и деплоя | ключи по умолчанию, записанные строкой |
| Миграции базы | коды и пароли как значения по умолчанию |
| CI/CD (GitHub Actions и т.п.) | секреты, выведенные в лог |

### Ключи известных форматов

Эти шаблоны почти никогда не дают ложных срабатываний:

```
sk-…                       ключ OpenAI
ghp_… / github_pat_…       токен GitHub
AKIA…                      ключ AWS
AIza…                      ключ Google
eyJ…                       JWT (смотреть, что внутри)
-----BEGIN … PRIVATE KEY   приватный ключ
```

### Отдельно: последняя строка миграции

Классика, которую пропускают: в SQL-миграции записан код доступа как значение по
умолчанию. Хеширование не спасает — исходное значение написано в том же файле строкой
выше и лежит в git навсегда.

### Что делать с находкой

Не «удалить и закоммитить». Ключ, который был в репозитории, **считается известным
злоумышленнику**. Порядок: выпустить новый → обновить везде, где используется →
отозвать старый → вычистить историю. Именно в таком порядке: если отозвать первым,
сервис упадёт. Подробно — `guard-server`, `guard-server/references/secrets.md`.

## Блок 2. Периметр

**Что ищем:** что видно из интернета.

### Проверка портов

Изнутри сервера видно всё, поэтому проверка изнутри бесполезна. Два взгляда:

```bash
# Что слушает сервер (выполнять на сервере)
ss -tulpn | grep LISTEN
```

Ключевое — колонка адреса:

| Что видно | Что это значит |
|---|---|
| `127.0.0.1:5432` | Только сам сервер. **Правильно** |
| `0.0.0.0:5432` | Весь интернет. **Красный уровень** |
| `:::5432` | То же самое, через IPv6 |

Снаружи, с другой машины:

```bash
# Ответил ли порт — проверять только СВОЙ сервер
nc -zv ваш-домен.ru 5432
nc -zv ваш-домен.ru 6379
```

Что не должно отвечать снаружи никогда: база данных (5432, 3306, 27017), Redis (6379),
Elasticsearch (9200), панели администрирования, метрики, очереди, Docker API (2375).

### Docker в обход firewall

Отдельная проверка, потому что это ловушка. Docker пишет правила в iptables **мимо ufw**.
Порт, проброшенный как `-p 5432:5432`, открыт в интернет, даже если `ufw status`
показывает, что всё закрыто.

Проверить: в `docker-compose.yml` и командах запуска все пробросы должны быть вида
`127.0.0.1:ПОРТ:ПОРТ`, а не `ПОРТ:ПОРТ`.

### TLS

- есть ли HTTPS и перенаправляется ли http;
- когда истекает сертификат и настроено ли автопродление;
- не отключена ли где-то в коде проверка сертификата
  (`verify=False`, `rejectUnauthorized: false`).

Третий пункт скрипт ловит в блоке 3 аудита кода — он встречается чаще, чем кажется,
и полностью обесценивает HTTPS.

## Блок 3. Заголовки и CSP

**Что ищем:** что сервер говорит браузеру о правилах безопасности.

```bash
curl -sSI https://ваш-домен.ru/ | grep -iE 'strict-transport|content-security|x-content-type|referrer|permissions|x-frame'
```

| Заголовок | Нет его — что это значит |
|---|---|
| `Strict-Transport-Security` | Первый запрос можно перехватить и увести на подделку |
| `Content-Security-Policy` | Чужой скрипт, попавший на страницу, выполнится без помех |
| `X-Content-Type-Options: nosniff` | Загруженная «картинка» с кодом может выполниться |
| `Referrer-Policy` | Чужие сайты видят адреса ваших внутренних страниц |
| `Permissions-Policy` | Страница может просить камеру, микрофон, геолокацию |
| `X-Frame-Options` / `frame-ancestors` | Сайт встраивается в чужую страницу — подмена интерфейса |

### На что смотреть в самом CSP

Наличие CSP ещё не значит, что он работает:

- `script-src 'unsafe-inline'` — разрешает встроенные скрипты, то есть почти сводит
  защиту на нет. Главное, что нужно убрать;
- `script-src 'unsafe-eval'` — разрешает выполнение строк как кода;
- `default-src *` — разрешает всё;
- отсутствие `frame-ancestors` — сайт можно встроить;
- отсутствие `base-uri` — можно подменить базовый адрес и увести загрузку скриптов.

### Что сервер рассказывает о себе

`Server: nginx/1.18.0` и `X-Powered-By: PHP/7.4` — это подсказка сканеру: версия
известна, дальше подбирается готовый эксплойт. Убирается одной строкой
(`server_tokens off`). Не уязвимость, но бесплатно закрывается.

### Служебные файлы наружу

Проверить, что не открываются: `.env`, `.git/config`, `docker-compose.yml`,
`package.json`, `backup.sql`, `.DS_Store`, `phpinfo.php`, `/server-status`.

Открытый `.git/` — красный уровень: по нему выкачивается **весь исходный код проекта
вместе с историей**, а значит и все секреты, которые когда-либо в нём были.

## Блок 4. Зависимости

**Что ищем:** известные уязвимости в чужом коде, который вы используете.

### Базовое

```bash
npm audit --omit=dev        # Node
pip-audit                   # Python
composer audit              # PHP
govulncheck ./...           # Go
```

Или универсально — [osv-scanner](https://github.com/google/osv-scanner):

```bash
osv-scanner scan source -r .
```

### Как читать результат и не утонуть

Сканер почти всегда выдаёт длинный список. Разбирать его надо не по цвету, а по
двум вопросам:

1. **Уязвимая функция вообще вызывается в вашем коде?** Уязвимость в функции разбора
   SVG в библиотеке, которой вы разбираете только JSON, вас не касается.
2. **Пакет боевой или только для сборки?** Уязвимость в инструменте сборки не попадает
   к пользователям. Поэтому `--omit=dev`.

Это не повод игнорировать — это повод не тратить неделю на красные строчки,
пока настоящая дыра в экспорте клиентской базы стоит незакрытой.

### Lock-файл

`package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` **обязан лежать в git**. Без него
сборка на сервере поставит другие версии, чем вы проверяли, — включая версию, которую
вчера подменил взломанный аккаунт сопровождающего.

### Новые зависимости

При аудите проекта, который уже живёт, отдельно посмотреть свежие добавления:

```bash
git log -p --since="3 months ago" -- package.json | grep '^+' | grep -v '^+++'
```

Пакет, добавленный ради одной функции, тянет за собой десятки чужих и получает доступ
ко всему, что есть у сборки. Это самый быстрорастущий способ атаки за последние годы.

## Итог блоков 1–4

Что здесь считается красным уровнем:

| Находка | Почему красный |
|---|---|
| Секрет в коде или в git | Обнуляет все остальные слои |
| База или Redis открыты наружу | Находят сканеры за час, дальше подбор |
| Открыт `/.git/` | Выкачивается весь код и вся история |
| Открыт `.env` | Все ключи по прямой ссылке |
| Отключена проверка сертификата | HTTPS перестаёт что-либо значить |
| Нет CSP на системе с чужим вводом | Вставка кода проходит без сопротивления |

Всё остальное — оранжевое и жёлтое, в плановом порядке.
